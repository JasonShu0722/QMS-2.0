# QMS 2.0 开发治理

本文件是 QMS 2.0 功能开发、维护和扩展的统一入口。它把需求、实现、验证证据和后续维护连接起来；不能替代产品规格、领域交接文档或真实验收记录。

## 1. 任务模板

每个功能或缺陷任务开始前，在对应阶段计划或任务记录中填写以下内容：

跨层任务、依赖升级和维护变更同时使用[变更影响分析](CHANGE-IMPACT.md)。术语查[业务术语](DOMAIN-GLOSSARY.md)，既有选型查[架构决策](ARCHITECTURE-DECISIONS.md)，发布与故障处置查[维护手册](OPERATIONS-RUNBOOK.md)。这些入口引用原始规格，不扩大业务交付范围。

```markdown
## 任务

- 目标：
- 非目标：
- 交付单元及分组理由、需求编号 / 实际记录 ID 与 Issue / 分支 / PR 映射：
- 动作授权范围及各阶段前置条件：
- 当前状态：
- 状态差距：
- 影响模块：
- 影响用户和业务流程：
- API / OpenAPI 变化：无 / 有，说明：
- 数据库 / 迁移变化：无 / 有，说明：
- 权限、数据范围和流程权限变化：无 / 有，说明：
- 审计、通知、附件和 Worker 变化：无 / 有，说明：
- 验收标准：
- 失败、冲突和回滚路径：
- 完成证据位置：
- 最终版本回归、Issue 关闭与协作台账回填顺序、完成条件及失败接续：
- 拟沉淀的规则 / 经验、目标权威文件、适用边界及验证方式：
```

任务执行顺序固定为：理解现状 → 固定目标和边界 → 制定可验证步骤 → 最小范围修改 → 针对性验证 → 独立审查 → 更新文档和状态 → 阶段门禁。

目标、范围或验收标准发生变化时，必须在任务记录中写出变更原因、差异和授权，不得在实现过程中静默扩大或降低目标。

设计与计划阶段就要列出交付闭环和沉淀子任务，执行、回归、关闭及规则更新依[需求交付与功能维护流程](DELIVERY-MAINTENANCE-PROCESS.md)。相同目标可合并多个需求记录，但必须保留逐需求授权与验收；同一批相互影响的交付单元在最终集成版本上回归。沉淀项随实际结果复核，没有新的可复用规则时记录理由，不强行新增要求或复制专项设计。

## 2. 功能交付证据矩阵

每项跨层功能必须完成下表。无关项填写“不适用”并说明理由；不能用“代码存在”代替行为证据。

| 交付面 | 需要证明的事实 | 证据 |
| --- | --- | --- |
| 需求与领域 | 业务目标、非目标和领域规则已经冻结 | 规格或任务记录 |
| API | DTO、错误和权限行为符合 OpenAPI | API 测试、Swagger 和 `contracts:check` |
| 数据库 | 迁移、约束、历史读取和回滚行为正确 | 真实 PostgreSQL 集成测试 |
| Web | 加载、空态、错误、权限、冲突和未保存状态可操作 | Web 单测和浏览器测试 |
| 功能权限 | 允许角色可以操作，其他角色被拒绝 | 允许/拒绝测试 |
| 数据范围 | 内部组织和供应商隔离正确 | 跨组织允许/拒绝测试 |
| 流程权限 | 当前节点处理、审批、验证和关闭规则正确 | 流程运行时测试 |
| 审计 | 成功、拒绝、冲突和回滚留下正确业务审计 | 审计测试或验收日志 |
| 通知与 Worker | 排程、重试、幂等、失败队列和恢复正确 | 真实 Worker 测试 |
| 附件 | 资源授权、扫描、版本、下载和删除边界正确 | 真实对象存储/扫描测试 |
| 运维 | 健康检查、日志、追踪、恢复和回滚路径明确 | 运维记录或演练证据 |
| 文档 | 规格、交接、命令和状态入口同步 | 文档差异与链接检查 |

## 3. 分层质量门禁

| 层级 | 使用时机 | 最低门禁 |
| --- | --- | --- |
| 修改级 | 单文件或局部逻辑修改 | 相关单测、Lint、`git diff --check`、`check:governance` |
| 功能级 | API、数据库、Web 或跨层功能完成 | 交付证据矩阵、真实 PostgreSQL、契约同步、受影响 Web/API 测试 |
| 模块级 | 领域模块或平台能力合入 | 模块边界检查、权限允许/拒绝、Worker/附件/审计相关真实测试 |
| 阶段级 | 阶段计划或主目录整合完成 | `acceptance:phase-1` 或 `acceptance:phase-2`，并更新 `FOUNDATION.md` 或对应阶段记录 |
| 发布级 | 进入正式部署前 | 发布版本、迁移、备份恢复、TLS、安全配置、回滚验证和未覆盖范围记录 |

失败时先判断失败属于动作、方案、目标还是环境；同一尝试没有减少状态差距时，必须切换诊断路径或暂停，不得通过跳过、Mock、降低断言或复用旧 PASS 制造通过。

## 4. 独立审查规则

以下变更必须由没有参与主要实现的上下文重新阅读需求、差异和证据：

- 供应商数据隔离、权限目录、角色分配或身份边界。
- 流程发布、流程版本、简报升级、审批、验证和关闭。
- 幂等、并发、锁顺序、CAS、事务回滚和 Worker 重复消费。
- 数据库迁移、历史数据兼容、备份恢复和密钥轮换。
- 附件资源授权、扫描状态、对象版本和下载。

独立审查至少回答：范围是否漂移、是否存在越权路径、失败是否原子回滚、证据是否真实可复查、是否影响已有模块和历史数据。审查结论必须记录阻断项、建议项、验证命令和复核结果。

## 5. 模块边界

API 领域模块通过公开服务和模块导出协作。新增跨模块依赖必须同时更新 `governance/module-boundaries.json` 和本文件的领域边界说明；直接导入其他模块 Controller 属于禁止行为。

当前允许的依赖对以机器可读清单为准，运行以下命令检查：

```powershell
corepack pnpm check:governance
```

模块不得通过读取其他模块内部表来绕过服务边界。跨模块查询应通过公开服务或专门读取模型完成；公共权限、编号、附件、流程和审计能力只能由其所属模块提供。

## 6. 状态和文档同步

功能完成、阶段验收、试点放行和生产发布是不同状态，必须更新 `CAPABILITY-STATUS.md` 的对应字段。新增或废弃 Markdown、`AGENTS.md` 或治理 JSON 时，必须同步更新 `docs/README.md` 和 `governance/documentation-index.json`。交接文档保留历史记录，但最新状态必须明确日期、源码范围、验证命令、实际结果和限制。

文档链接、权威来源与复核有效性按[文档复核机制](DOCUMENTATION-MAINTENANCE.md)检查。来源变化后先核对内容再更新复核记录；不得以批量刷新日期或摘要替代实际复核。

## 7. 完成判定

只有同时满足以下条件，任务才可以标记完成：

1. 目标和非目标没有未处理冲突。
2. 交付证据矩阵中的适用项均有证据。
3. 相关测试、构建、契约和门禁通过。
4. 高风险变更已经独立审查。
5. 文档、能力状态和回滚路径已经同步。
