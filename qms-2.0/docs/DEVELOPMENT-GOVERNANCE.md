# QMS 2.0 开发治理

## 新增功能的管理员默认授权

负责人2026-11-14明确要求后续开发新增的全部内部功能默认向管理员开放。有效 `platform:admin` 通过既有活跃内部权限投影获得新增权限，同时登记管理context和导航入口；管理员必须能看到并完成获准操作，不能只更新权限目录。默认授权不依赖账号名称，不复制权限到每个岗位，不放宽组织/供应商/业务节点边界，也不自动启用尚未配置的外部入库规则。既有明确专项授权例外保持原义。每次新增功能验收包含真实管理员默认可用、普通无授权拒绝及失效组织/身份拒绝；规则写入本文件和AGENTS后，后续任务必须读取并执行。

负责人2026-11-17要求权限配置随功能迭代同步。新增、拆分或调整内部功能时，交付清单必须同时核对权限目录分组及中文动作名、数据库可授予权限、岗位授权选择器、菜单/context/真实路由、按钮、后端业务与幂等重放守卫。权限按实际职责和风险拆分，不能把新业务长期隐藏在泛化的“平台配置维护”中，也不为每个按钮生成无实际消费者的权限。拆分存量权限须证明旧岗位有效能力等价且不扩大，新增高风险能力不得因原写权自动回填；管理员默认可用与普通岗位可配置/未授权拒绝分别验证。

本文件是 QMS 2.0 功能开发、维护和扩展的统一入口。它把需求、实现、验证证据和后续维护连接起来；不能替代产品规格、领域交接文档或真实验收记录。

本文件权威维护任务摘要、证据矩阵、质量门禁、独立审查与工程完成条件；阶段授权、版本、发布和关闭回填依[交付流程](DELIVERY-MAINTENANCE-PROCESS.md)，操作环境依[工程工具](ENGINEERING-TOOLS.md)，机器人分析和字段职责依[OpenClaw 协作说明](OPENCLAW-OPS-HANDOFF.md)。

## 1. 任务模板

### 当前摘要（放在对应计划顶部）

负责人已确认使用现有计划维护当前摘要，不另建任务状态平台。每个交付单元在开始、检查点变化、中断恢复和结束时更新下列内容；合并多个 REQ 时保留逐需求的批准与验收差异。

| 摘要项 | 记录要求 |
| --- | --- |
| 最后核对时间与范围 | 日期 / 时区、目标与非目标、对应设计 / 计划 |
| 批准与动作授权 | 来源、批准范围快照，以及本地开发 / Issue / PR / 合并发布 / 关闭回填分别是否获准 |
| 定位与版本 | REQ / 实际 record_id → Issue → 分支 → PR；分配版本、源码基线 / 当前 HEAD、部署 SHA 分开 |
| 当前检查点与分别状态 | 本地工程、PR、部署、最终验收、Issue 关闭、回填和 Git 同步分别记录实际进度；不适用附理由 |
| 证据与限制 | 实际覆盖、来源、对应版本和 Git 外证据位置；未知、失败或缺失前置明确写出 |
| 下一动作与负责人 | 已获准时应主动执行的具体动作；未获准或阻塞时写缺口，不把动作列为笼统建议 |

摘要是检索入口，不替代实时回查、源码验证或外部事实。后续变化不得覆写历史验收来源；旧“当前”段标明阶段日期并指向顶部摘要。已结束任务再次接续时核对是否有剩余同步或新缺陷，不根据旧未勾选项重新开发。没有影响能力状态的纯文档任务，不机械更新业务能力总账。

### 工程任务明细

每个功能或缺陷任务开始前，在对应阶段计划或任务记录中填写以下内容：

跨层任务、依赖升级和维护变更同时使用[变更影响分析](CHANGE-IMPACT.md)。术语查[业务术语](DOMAIN-GLOSSARY.md)，既有选型查[架构决策](ARCHITECTURE-DECISIONS.md)，发布与故障处置查[维护手册](OPERATIONS-RUNBOOK.md)。这些入口引用原始规格，不扩大业务交付范围。

```markdown
## 任务

- 目标：
- 非目标：
- 交付单元及分组理由、需求编号 / 实际记录 ID 与 Issue / 分支 / PR 映射：
- 动作授权范围及各阶段前置条件：
- 当前检查点、授权来源及下一主动动作（纯文档免 Issue / PR 时注明）：
- 当前状态：
- 状态差距：
- 影响模块：
- 工作台功能图谱：受影响能力 ID、入口、业务规则／联动及使用指南；不适用时说明原因：
- 影响用户和业务流程：
- API / OpenAPI 变化：无 / 有，说明：
- 数据库 / 迁移变化：无 / 有，说明：
- 权限、数据范围和流程权限变化：无 / 有，说明：
- 审计、通知、附件和 Worker 变化：无 / 有，说明：
- 验收标准：
- 失败、冲突和回滚路径：
- 完成证据位置：
- 验收前置：角色 / 会话、浏览器 / 真实设备、服务及缺项处理：
- 证据来源、实际覆盖、未知明细及源码 / 部署版本：
- 最终版本回归、Issue 关闭与协作台账回填顺序、完成条件及失败接续：
- 拟沉淀的规则 / 经验、目标权威文件、适用边界及验证方式：
```

常规任务执行顺序为：理解现状 → 固定目标和边界 → 复用 / 创建 Issue → 制定可验证步骤 → 最小范围修改 → 验证与独立审查 → 主动提交 PR → 获准集成发布 → 最终回归 → 关闭回填与归档。阶段门禁随对应检查点执行；仅本地和纯文档分支按交付流程处理，不机械执行不适用步骤。

目标、范围或验收标准发生变化时，必须在任务记录中写出变更原因、差异和授权，不得在实现过程中静默扩大或降低目标。

设计与计划阶段就要列出交付闭环和沉淀子任务，执行、回归、关闭及规则更新依[需求交付与功能维护流程](DELIVERY-MAINTENANCE-PROCESS.md)。相同目标可合并多个需求记录，但必须保留逐需求授权与验收；同一批相互影响的交付单元在最终集成版本上回归。沉淀项随实际结果复核，没有新的可复用规则时记录理由，不强行新增要求或复制专项设计。

## 2. 功能交付证据矩阵

每项跨层功能必须完成下表。无关项填写“不适用”并说明理由；不能用“代码存在”代替行为证据。

| 交付面 | 需要证明的事实 | 证据 |
| --- | --- | --- |
| 需求与领域 | 业务目标、非目标和领域规则已经冻结 | 规格或任务记录 |
| API | DTO、错误和权限行为符合 OpenAPI | API 测试、Swagger 和 `contracts:check` |
| 数据库 | 迁移、约束、历史读取和回滚行为正确 | 真实 PostgreSQL 集成测试 |
| Web | 加载、空态、错误、权限、冲突和未保存状态可操作 | Web 单测和浏览器测试 |
| 功能权限 | 允许角色可以操作，其他角色被拒绝 | 允许/拒绝测试 |
| 数据范围 | 内部组织和供应商隔离正确 | 跨组织允许/拒绝测试 |
| 流程权限 | 当前节点处理、审批、验证和关闭规则正确 | 流程运行时测试 |
| 审计 | 成功、拒绝、冲突和回滚留下正确业务审计 | 审计测试或验收日志 |
| 通知与 Worker | 排程、重试、幂等、失败队列和恢复正确 | 真实 Worker 测试 |
| 附件 | 资源授权、扫描、版本、下载和删除边界正确 | 真实对象存储/扫描测试 |
| 运维 | 健康检查、日志、追踪、恢复和回滚路径明确 | 运维记录或演练证据 |
| 文档 | 规格、交接、命令和状态入口同步 | 文档差异与链接检查 |

每条验收记录包含：需求 / 检查项、前置角色与环境、源码或部署 SHA、预期、实际结果、来源（代理执行 / CI 执行 / 负责人手动确认）、执行或确认时间、证据位置、实际覆盖和未知明细。来源必须与事实相符，用户确认原话不能转写成代理执行命令；具体型号等未提供时注明未知，不补造材料。

证据应区分 PASS、FAIL、未执行 / 阻塞与不适用。所用工具已有固定状态名时沿用其定义，不把人工确认塞进机器报告的 PASS；人工验收是否足够按批准计划和[交付流程](DELIVERY-MAINTENANCE-PROCESS.md)判断。页面 / 服务健康、资源指纹一致只证明对应事实，不证明所有权限、扫描或业务主链完成。

## 3. 分层质量门禁

| 层级 | 使用时机 | 最低门禁 |
| --- | --- | --- |
| 修改级 | 单文件或局部逻辑修改 | 相关单测、Lint、`git diff --check`、`check:governance` |
| 功能级 | API、数据库、Web 或跨层功能完成 | 交付证据矩阵、真实 PostgreSQL、契约同步、受影响 Web/API 测试 |
| 模块级 | 领域模块或平台能力合入 | 模块边界检查、权限允许/拒绝、Worker/附件/审计相关真实测试 |
| 阶段级 | 阶段计划或主目录整合完成 | `acceptance:phase-1` 或 `acceptance:phase-2`，并更新 `FOUNDATION.md` 或对应阶段记录 |
| 发布级 | 进入正式部署前 | 发布版本、迁移、备份恢复、TLS、安全配置、回滚验证和未覆盖范围记录 |

失败时先判断失败属于动作、方案、目标还是环境；同一尝试没有减少状态差距时，必须切换诊断路径或暂停，不得通过跳过、Mock、降低断言或复用旧 PASS 制造通过。

## 4. 独立审查规则

以下变更必须由没有参与主要实现的上下文重新阅读需求、差异和证据：

- 供应商数据隔离、权限目录、角色分配或身份边界。
- 流程发布、流程版本、简报升级、审批、验证和关闭。
- 幂等、并发、锁顺序、CAS、事务回滚和 Worker 重复消费。
- 数据库迁移、历史数据兼容、备份恢复和密钥轮换。
- 附件资源授权、扫描状态、对象版本和下载。

独立审查至少回答：范围是否漂移、是否存在越权路径、失败是否原子回滚、证据是否真实可复查、是否影响已有模块和历史数据。审查结论必须记录阻断项、建议项、验证命令和复核结果。

## 5. 模块边界

API 领域模块通过公开服务和模块导出协作。新增跨模块依赖必须同时更新 `governance/module-boundaries.json` 和本文件的领域边界说明；直接导入其他模块 Controller 属于禁止行为。

REQ-0032 CP-1 的 `system-management` 只组合 Identity 的真实控制台 context、Organization 的待配置、Audit 的公开审计查询及 TaskNotification 的失败队列读取；认证入口复用 Authorization 的公开 `RequireAuthenticated` 装饰器，由全局守卫校验真实会话。CP-2 的运行服务聚合还通过 FileManagement 的公开安全汇总读取扫描/存储事实，邮件及投递由 Identity、失败事件归属及有限 Worker/PDF 回执由 TaskNotification 各自拥有；SystemManagement 不直接查询这些领域私表。API/交换观测模块只操作自身追加观测表，不绕过拥有者的数据范围与权限；Organization 到 Workflow 只使用公开的旧角色引用读取模型，保留稳定历史资格，不跨读流程私有表。

制程台账的人员名称筛选使用 Identity 公开的人员显示名称查询表达式，组织范围仍由制程台账查询约束。当前允许的依赖对以机器可读清单为准，运行以下命令检查：

```powershell
corepack pnpm check:governance
```

模块不得通过读取其他模块内部表来绕过服务边界。跨模块查询应通过公开服务或专门读取模型完成；公共权限、编号、附件、流程和审计能力只能由其所属模块提供。

## 6. 状态和文档同步

功能完成、阶段验收、试点放行和生产发布是不同状态，必须更新 `CAPABILITY-STATUS.md` 的对应字段。新增或废弃 Markdown、`AGENTS.md` 或治理 JSON 时，必须同步更新 `docs/README.md` 和 `governance/documentation-index.json`。交接文档保留历史记录，但最新状态必须明确日期、源码范围、验证命令、实际结果和限制。

文档链接、权威来源与复核有效性按[文档复核机制](DOCUMENTATION-MAINTENANCE.md)检查。来源变化后先核对内容再更新复核记录；不得以批量刷新日期或摘要替代实际复核。

### 工作台功能图谱随开发更新

自功能图谱首发起，新增、调整、优化、迁移或下线能力的交付单元必须把图谱纳入现有计划、PR 和验收回填。同一功能可多次迭代，节点主状态仅为“构想中”“开发中”“已上线”。无初版证据或只有占位时记“构想中”；有初版但未完成运行验证、未获明确认可或尚未发布的记“开发中”；基本功能经负责人或授权验收人明确认可且实际发布后，才记“已上线”。开工、PR 合并或部署成功单独均不足以升级状态。

| 检查点 | 责任与要求 |
| --- | --- |
| 需求与计划 | 开发负责人登记受影响能力 ID，注明变化范围、节点及关系、权威规则与操作指南；不适用要写原因。节点和板块名称以当前正式导航、页面、页签或操作标题为准，无页面能力引用权威规格，不使用样板自造分组。保留稳定 ID，旧名可作搜索别名。 |
| 实现与 PR | 开发负责人随同一交付更新受影响规则、节点、入口和联动条件，以及指南的适用版本、岗位、前置、操作步骤、结果和异常处理。新增或改名的正式入口应同步核对覆盖。审查人对照实际行为与证据核对，适用项缺失时不得通过交付审查。 |
| 发布、验收与关闭 | 验收人记录明确认可的能力范围、版本及验证结果；开发负责人核对发布事实、当前状态和对应指南，在原计划／Issue 回填证据及图谱更新出处。认可晚于发布时，按已有授权补更目录并回读；确认同步后才关闭适用项。回滚、停用或认可失效时按仍有效的版本和范围修正图谱与指南。 |

已上线能力后续优化不改变已认可且仍可用的基础状态，随优化同步更新受影响的规则、联动和指南，并标明适用版本。未发布的优化可记录于迭代说明，不覆盖当前线上操作指南。图谱更新随现有交付流程执行，不从 GitHub、飞书或部署日志后台自动推断，也不另建任务台账。

现存节点的状态可由有效平台管理员在图谱详情中调整，也可在代码交付中通过显式数据迁移调整。管理员保存走现有权限和审计；代码调整必须在原交付 PR 中列出能力 ID、目标状态、认可和发布依据，按[双路径实施约定](../../docs/superpowers/plans/2026-11-21-qms-workbench-capability-graph.md#状态配置与交付边界)只更新指定节点。普通发版不覆盖，最后一次成功应用的显式调整生效；回滚需要改变状态时另做显式调整，不反推生产状态。

## 7. 完成判定

只有同时满足以下条件，才能标记“本地工程完成”；这不是发布或交付闭环完成：

1. 目标和非目标没有未处理冲突。
2. 交付证据矩阵中的适用项均有证据。
3. 相关测试、构建、契约和门禁通过。
4. 高风险变更已经独立审查。
5. 文档、能力状态和回滚路径已经同步。

需要同步的资产以实际影响为准；纯文档执行相关格式、治理和规则复核，不为形成证据启动无关业务服务。规格 / 质量审查要求继续按项目流程路由执行，以上高风险独立审查条件不减免该路由。

PR、部署、最终验收、关闭回填和 Git 归档按[交付流程完成定义](DELIVERY-MAINTENANCE-PROCESS.md)分别判定；只能报告有证据的实际阶段。机器检查、代理执行与负责人手动确认继续使用第 2 节格式，不能互相替代或补造结果。
