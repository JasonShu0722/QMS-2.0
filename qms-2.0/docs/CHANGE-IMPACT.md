# 变更影响分析与能力复用

本页扩展[开发治理](DEVELOPMENT-GOVERNANCE.md)的任务模板，适用于新功能、缺陷修复、依赖升级和维护变更。每次任务只填写适用项，不适用必须给出原因；最终门禁仍以开发治理和阶段计划为准。

可先运行 `corepack pnpm validation:recommend` 获取当前 Git 改动的检查建议与文档复核入口；规则、可选基线和未知路径处理见[变更验证推荐](VALIDATION-IMPACT.md)。推荐不代替本页的业务影响分析或实际验收。

## 分析顺序

1. 根据[术语](DOMAIN-GLOSSARY.md)和领域交接确认谁拥有业务事实、谁是消费者。
2. 列出直接修改和间接受影响的 API、Web、Worker、数据库、历史记录与运维流程。
3. 优先复用现有 QMS 公开服务，其次使用已采用依赖的能力；引入新依赖前比较许可证、维护状态、安全支持、运行成本、数据出口和替换路径。将核实日期及官方来源写入任务，不凭过往印象判定。
4. 检查[决策索引](ARCHITECTURE-DECISIONS.md)；跨模块依赖以 `governance/module-boundaries.json` 为准。依赖表只提供导入影响线索，不能证明授权、事务或数据库访问正确。
5. 为允许、拒绝、并发、重复、回滚和旧数据读取列出实际验证；关联来源文档后同步复核记录。

## 示例：新增领域正式发单

领域服务拥有专业事实，复用编号、问题索引、固定版本流程、审计与 Outbox；在同一事务内提交。先验证缺绑定时无残留、同键重放不重复创建、变更 payload 被拒绝、并发只有一个胜者、审计失败全部回滚。供应商只能读取已释放且属于本企业的记录；正式回复和证据需另行接入领域约束。此示例是分析方法，实际交付范围查[阶段三](PHASE-3.md)，不能据此宣称主链已完成。

数据库变更至少验证空库迁移、旧版本数据升级、历史读取和失败处置；应用回退不等于数据库自动降级。涉及身份、事务、迁移或证据授权时，按开发治理执行独立审查。
