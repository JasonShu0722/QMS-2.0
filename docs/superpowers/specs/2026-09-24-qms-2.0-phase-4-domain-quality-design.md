# QMS 2.0 阶段四业务域设计规格

- 日期：2026-09-24
- 状态：阶段三开发 PASS 后启动策划
- 参考：`E:/WorkSpace/QMS/archive/qms-1.0/.kiro/steering/product.md`、`E:/WorkSpace/QMS/archive/qms-1.0/doc/requirements-panel/QMS_FUNCTION_REQUIREMENTS.md` 及 1.0 各领域实现记录
- 适用范围：制程质量、客户质量、新品质量、审核管理

## 1. 设计结论

阶段四沿用 QMS 1.0 已记录的业务组织方式，但不复制 1.0 的代码、表结构、编号规则或兼容层。每个领域先拥有自己的来源台账，再由业务人员从台账筛选、分流并发起正式问题；正式问题进入 QMS 2.0 已验收的问题索引、版本化流程、任务通知、附件、审计和报告链路。

```text
外部/人工/业务数据 → 领域来源台账 → 选择与分流 → 正式问题/简报/8D → 验证与关闭 → 追溯与经验沉淀
```

来源台账不是公共问题索引的替代品，也不自动等于正式问题。正式问题必须保留来源记录关系、来源快照和发起人决策；同一来源可以被多个正式问题引用，但同一发起动作必须幂等。

## 2. QMS 1.0 参考与 QMS 2.0 转换

1.0 的 `process_defects` / `process_issues`、`customer_complaints` / 客诉 8D、`new_product_project` / `trial_production` / `trial_issue`、`audit_plan` / `audit_execution` / `audit_nc` / `customer_audit` 提供业务语义参考。2.0 只吸收业务规则和用户路径：

- 专业事实仍由领域模块拥有，公共问题索引只保存聚合字段和稳定引用。
- 领域发单调用平台 start/action/upgrade 事务边界，不在领域内复制状态机、编号器或 Worker。
- 1.0 的简单问题、复杂问题和 8D 分流转换为 2.0 的问题简报/8D 固定流程绑定。
- 1.0 的待通知、延期、逾期升级等预留只在 2.0 有真实平台证据时接入，不把历史占位实现当作已交付能力。
- 1.0 双环境、旧编号和旧数据迁移不纳入阶段四。

## 3. 阶段四范围

### 3.1 制程质量：不良品来源台账→制程问题

第一入口是不良品台账，支持人工补录、批次/工单/工序/产线、失效现象字典、数量、责任类别、物料和供应商关联、证据及历史查询。责任类别至少覆盖物料、作业、设备、工艺和设计不良；IMS 指标的分母、趋势和外部来源边界在接口核实前只保留定义，不生成假趋势。

PQE 可从台账或质量趋势中选择一条或多条记录发起正式问题，填写责任板块、围堵、原因分析和验证要求。正式问题保存来源关系；问题关闭不删除或覆盖原始不良记录。

MES/IMS 只做接口预留：阶段四定义外部来源标识、字段映射、幂等键、同步批次、失败重试和审计边界，保留内部 `ProcessDefectSourceAdapter` 接口及未来入口约定；在 MES 字段、认证、推送方向和验收样本核实前，不启动真实连接、轮询任务或成功替身。人工录入必须独立可用。

### 3.2 客户质量：客诉来源台账→问题/8D

第一入口是客诉台账，至少区分 0KM 和售后客诉，并记录客户主数据、终端客户、产品、缺陷、失效里程、购车日期、VIN、是否退件、是否需要实物解析、严重度和来源证据。严重度必须映射升级规则、响应/整改 SLA 与审批级别。客诉台账支持退件接收、账务、返修或报废、责任和状态跟踪，以及实物处理和一次原因分析的独立分支。

客户质量负责人可以从一条或多条客诉记录发起问题简报或 8D；发起后仍可在授权范围内增删客诉来源，并保留关联历史与主来源切换审计，禁止移除最后一条来源。需要解析的客诉必须先完成失效分析输入或明确缺失状态；不需要解析的客诉可以留在台账处置，不强制创建正式问题。正式问题使用平台验证、关闭和归档，不复制 1.0 客诉状态机。QMS 1.0 对严重度具体等级仍标为待定，因此阶段四使用可版本化的严重度政策，不硬编码未经确认的映射；8D 的 7/10 工作日要求必须有工作日历证据，不能以现有分钟计时替代。

出货数据、IMS 追溯、索赔和 0KM/3MIS/12MIS 指标作为分阶段依赖：先冻结客户主数据和来源关系，再接真实外部数据；未核实的 ERP/SAP/IMS 接口只登记契约，不宣称集成完成。

### 3.3 新品质量：制程不良遴选→新品项目问题

新品项目先建立项目、阶段、交付物和试产批次，再从制程质量不良品台账按项目、产品、工单、批次或来源标识遴选新品相关记录。遴选结果保存来源引用和项目上下文，不复制一份脱离原始不良事实的新品不良。

项目立项时推送历史制程问题，项目成员必须逐条确认规避措施并上传证据后才能通过阶段门。遴选结果可以生成新品问题清单；简单问题走问题简报，复杂问题升级为 8D。试产问题必须支持责任跟踪、验证、关闭及遗留问题标记；带病量产必须经过明确审批和风险签署，不能通过普通关闭动作绕过。试产指标至少支持投入、产出、一次合格、不良、CPK 和尺寸等人工记录、来源标识和红绿灯报告。

新品项目还包括 1.0 记录的经验教训反向注入、阶段评审交付物互锁、试产目标与实绩、量产移交归档。IMS 工单数据和试产指标先通过可替换适配器接入，未确认外部接口时允许人工补录并明确数据来源。

### 3.4 审核管理：审核台账/执行→NC→正式问题

审核管理包括年度计划与排程、体系/过程/产品/二方审核模板、现场或移动执行、检查表结果、NG 分级与评分报告、审核资料归档和客户/二方审核台账。审核提交后产生的 NG 条款进入 NC 清单，保留审核、条款、照片或文件证据和责任部门关系；严重度映射一般 30 天、严重 7 天等整改期限，并支持延期审批和逾期升级。

NC 支持责任分派、原因与措施、整改证据、审核员验证、退回重提、逾期升级和关闭。需要进入统一问题中心的 NC 通过领域适配器创建正式问题，保留 NC 来源和审核快照；客户/二方审核的问题清单导入后也必须逐条形成可追溯的内部来源记录。

审核计划延期、提醒、移动录入、客户审核附件导入和报告输出按真实平台能力分批交付；历史文档中的预留通知或定时任务不作为完成证据。

## 4. 共享边界与不变量

- 各领域拥有来源台账、专业字段、专业读写规则和来源快照；不得直接读取其他领域内部表。
- 发单统一使用领域服务→问题索引→流程 runtime→审计/Outbox 的同事务边界。
- 来源关系支持一对多和多对多，但删除来源记录不能删除正式问题；来源变更必须留下审计。
- 所有写操作使用 CSRF、幂等键、版本 CAS 和服务端数据范围；客户端不得提交可信组织、责任人或流程版本。
- 正式问题的编号、简报/8D 切换、任务通知、附件扫描、验证人与关闭人分离复用平台能力。
- 外部接口均采用适配器端口；未确认的 MES、IMS、ERP/SAP 不创建假数据、Mock 成功响应或静默跳过的验收。

## 5. 阶段四交付顺序

1. 4.0：冻结来源台账→正式问题的共享契约、来源关系、发单幂等协议和权限矩阵。
2. 4.1：制程不良品台账与人工录入，定义 MES/IMS 预留适配器契约，再接制程问题发单。
3. 4.2：客户主数据、客诉台账、实物处理/解析分流，再接问题简报/8D 发单。
4. 4.3：新品项目、经验教训、阶段评审、试产批次，接入制程不良遴选和新品问题闭环。
5. 4.4：审核计划、模板、执行、NC 和客户审核台账，接入正式问题与整改闭环。
6. 4.5：跨域真实浏览器主链、失败恢复、权限撤回、外部接口边界和阶段验收。

## 6. 阶段四非目标

- 不复制 QMS 1.0 的 FastAPI/SQLAlchemy/Vue 实现或旧编号。
- 不建设通用大表单、通用 BPMN、任意脚本执行或跨域万能创建入口。
- 不在 MES/IMS/ERP/SAP 字段和认证未确认前实现真实连接。
- 不把供应商绩效、供应商审核、PPAP、质量成本、仪器计量或 AI 自动决策混入本阶段主链。

## 7. 完成门槛

每个领域必须有来源台账真实 CRUD、来源到正式问题的原子发单、允许/拒绝权限、来源关系追溯、幂等/CAS/回滚、真实 PostgreSQL、生成契约、Web 冲突恢复和浏览器主链证据。阶段总体验收还必须覆盖制程来源→问题、客诉来源→问题/8D、制程来源→新品项目→新品问题、审核执行→NC→问题四条链，并明确外部系统未接入范围。
