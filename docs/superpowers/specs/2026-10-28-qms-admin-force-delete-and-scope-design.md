## 1. 调查结论与证据等级

### 1.1 用户删除确实缺产品能力

`qms-2.0/apps/api/src/modules/identity/admin-user.controller.ts`无DELETE入口；权限目录有read/create/update/status/transfer/reset，无`account:users:delete`；`UserAdministration.tsx`只有启停等操作。不是某个按钮单纯被隐藏，更不能把可重新启用的停用当成删除。

组织/部门已有普通删除，但`organization.service.ts:218`及`:308`仍把角色/授权、用户、岗位、任职和业务历史引用作阻断；`organization-initialization.ts`仍需精确来源匹配才能清初始化角色。旧“先证明初始化”机制不满足现在的强删目标，本轮应替换删除语义，不继续为每种旧记录补一条溯源特例。

### 1.2 跨组织失权已复现同形，现场身份尚未读取

真实一次性PostgreSQL、当前编译控制器及权限服务，在一个最终回滚的事务内验证：

| 本地真实场景 | 主组织/目标组织结果 |
| --- | --- |
| 用户名admin、主组织普通管理角色、子组织自动ORGANIZATION_GOVERNOR | 主组织21项管理权限；子组织仅5项organization治理权限，用户读取实际403，与截图菜单形态一致 |
| 同一用户/角色临时补显式platform:admin，仅在本地回滚事务内 | 子组织140项适用内部权限，用户读取允许，不新增逐组织membership |
| 撤销本地marker | 立即恢复子组织5项，不依赖缓存 |

证据在Git外`admin-governance-next/admin-projection-probe.json`，status=PASS。没有生产授权变更或持久化测试数据；这是实际controller/service投影，不是认证HTTP/浏览器重现，不证明线上账号恰好缺marker。

源码链：`AdminOrganizationController.list`（identity/admin-organization.controller.ts:21）→`effectiveRoleGrants`/`projectEffectiveRoleGrants`（common/security/effective-role-grants.ts:102/:108）→每目标组织permissions→`AdminPage.tsx:74`按所选权限决定页签；`assertAdminAccess`及授权Guard继续在API端拒绝缺项。选择目标组织并未改变session里的真实userId/主组织，不应通过伪造actor或强行显示所有页签修复。

现有平台身份必须有有效内部来源和`platform:admin`；名字admin、主组织权限多、新建子组织的治理授权都不能替代身份。该marker迁移只登记权限，没有给真实旧账号自动补授。前轮交付保留了受控CLI，却没有完成此账号的生产身份核验/初始化，也没有在当前管理页面清楚区分两种管理员。这是需要本轮补齐的管理闭环，不把问题简单甩给用户“没配置”。

现场最小只读核验：实际actor UUID/主组织、`/api/v1/admin/organizations`的ZLGLB permissions、当前账号effectiveRoles/platformScope和来源有效性。如果目录仅5项追marker来源；目录全量但页签缺追Web；页签有而API403追scope/后端。未读取这些事实前不宣布已确定线上根因，不按用户名批量升级账号。

## 2. 统一规则：当前配置、管理身份、历史事实分开

### 已确认，不再反复询问

1. 必须有可执行的组织/部门（含科室）/用户强制删除，不能“有引用就永久不能删”。角色、授权、任职历史、日志、回执或上传/审批历史的存在只进入影响清单，不作为业务删除阻断。
2. 可解除的当前配置自动转空/失效，之后涉及时提示补配；不强制管理员先手工清几十张表。
3. 平台管理员在所有内部组织具有统一适用管理能力，新增内部组织自动适用；不逐组织重复配置同一个超级账号。前端菜单、接口、批量/导入/导出、候选目录及ORM/SQL投影必须一致。
4. 保留业务、原审批/签署、文件版本及审计；删除身份不等于删除所有曾经由该人/组织操作的数据。

### 推荐技术取舍（实现前固定）

采用“永久删除当前可用对象，后台仅保留不可用历史身份”的小方案。删除后从正常组织树、用户列表、登录、人员/岗位候选和新业务配置彻底退出；有明确deletedAt，不是DISABLED换文案，也不允许普通启用/PATCH/回执重放复活。同代码/用户名可按既有唯一性口径重新建立，但必须新UUID、新凭证、无旧权限继承。

不选全库FK改可空或Cascade：真实130迁移结构清点已有92张表/102个直接组织外键；用户外键还存在Prisma未表达的签章、量产批准等SQL约束。organization_id和历史签署者不是当前可选配置，不能抹去租户归属、把历史改挂管理员或删掉不可变签章。后台留下历史身份不使它继续占用正常管理入口；只读历史展示“已删除组织/人员”和原必要身份快照。

若要求历史主键也物理抹除，需要另建历史归属实体并整体迁移复合FK/签署读取；比当前目标大，不作为本轮默认实现。归档访问权需由真实平台管理员/历史合法范围控制，不能把deleted/null当全组织可见。

## 3. 组织与用户强制删除的共同动作

| 数据类型 | 组织删除 | 用户删除 |
| --- | --- | --- |
| 活跃实体 | 标记永久删除，退出正常树/目录，不再可启用 | 标记永久删除，退出正常用户/人员目录，不再可登录或启用 |
| 凭证/权限 | 该组织有效授权及任职停止生效，账号进入待配置不能继续用旧组织登录 | 撤销全部会话/重置/MFA恢复等可复用凭证，移除个人有效授权、结束任职；不删共享岗位或别人的授权 |
| 可空现行配置 | 科室/岗位/分管、项目工程师建议、流程配置等逐类解除，统一待配置提示 | 工程师/负责人建议/当前领取者等逐类解除，其他人的事实与配置不被删除 |
| 未完成审批/任务 | 受影响资格失效，旧待审轮次取消有效状态、保留意见，补配后重新提交 | 同一处理，旧人无权继续批准；不能自动改成通过或默认管理员代审 |
| 已完成历史 | 原业务归属、已批准报告、原签章与审计保留 | 原actor/signer/创建者身份及不可变报告保留，不改成接任者 |
| 重建同名对象 | 新UUID，不继承旧scope/绑定/权限/业务 | 新UUID，新凭证，不继承旧签名/视图/任务/角色 |

当前各领域的“取消审批”和配置解除并没有一个现成覆盖所有身份变更的公开入口；要在本轮列出必要公开接缝、同事务/CAS及Worker读时复验，不能声称换一个数据库onDelete就全部完成。

只保留身份/范围授权、近期认证、版本/幂等、事务回滚及避免删光可登录平台管理员的技术安全。影响数量只展示，一次确认，不要求人工逐条拆除。删除原因可选，不额外发明复杂审批、强制输入代码或多轮确认。

**连带处置已确认：**组织下的用户和下级组织不被静默级联删除，父/主组织的当前配置解除并进入管理员可访问的“待配置”区；需要的账号/组织后续重配。部门/科室下的子部门保留并解除当前父关系，岗位保留但不得再以已删部门获取权限或分派；需补有效部门。普通业务接口不将失效身份当仍有效，后台历史归属继续保留。与此前自动提升到上级的技术建议不同，本次不擅自移动业务租户。

## 4. 平台管理员管理闭环

- 复用已有`platform:admin`、有效岗位/任职和ORM/SQL公共授权，不建立第二套超级账号白名单。已有受控初始化CLI保留；先精确核验当前实际账号来源，再按负责人批准的稳定ID完成初始化并回读，不从名字admin猜。
- 当前管理界面明确显示“平台管理员：全部内部组织”或“组织管理：当前授权范围”；角色来源与目标组织可见，不能让两个身份看起来完全一样。
- 管理目录返回实际目标scope与适用能力；切组织只换目标，不覆盖真实actor主组织。切换清除上一scope的敏感投影/待执行命令并abort旧请求，不能把A组织未知删除请求以B组织重放。
- 平台管理员统一具备组织、人员、岗位、目录/映射、平台和流程配置、审计、失败队列等适用管理功能。普通组织管理员仍只在批准范围内；供应商门户仍限本企业，不因平台视角跨企业开放。
- 管理配置权不等于替真实PQE/SQE/经理/部长签批；保留实际职责、同人双职责、四风险、已批准版本等已确认业务规则，不顺手建设任意管理员代审批旁路。

## 6. 拟定落地顺序与验收（仅策划，未开工）

1. 核验真实管理员来源并补可见身份/目标scope诊断，统一权限链；固定组织与用户删除生命周期、用户名/代码重用和历史读取规则。

3. 组织/用户删除入口及统一影响确认、已删除/待配置提示；切换范围、未知结果/401403/409/CAS/重复提交全链验证；生成Swagger契约供Web。
4. 一次集中真实PG/HTTP/Worker及浏览器矩阵，独立SPEC后QUALITY，再提交PR；合并/部署仍单独核准，不再把部署代码当已完成生产身份初始化。

| 核心场景 | 通过标准 |
| --- | --- |
| admin普通权限/显式平台身份、未来子组织、来源到期/撤权 | 不靠名字；平台身份所有内部组织适用功能一致；撤权立即生效；目录/菜单/API/SQL同口径 |
| 空组织/来源不全/自动或普通role-grant/用户任职/业务历史 | 强删成功，当前引用解除，历史不丢；不能仍只放行“空且可证明初始化” |
| 用户有上传、已签章、业务责任、日志/回执 | 当前账号永久删除且凭证失效；已签结果/历史actor保持，旧创建/恢复回执不可复活 |
| 待审核人或负责人被删 | 旧轮次不可继续批准，任务不误报已完成；补配后明确重新提交，旧报告/责任不冒名迁移 |
| 同代码/用户名/邮箱重建 | 真实数据库含SQL唯一索引验证，新UUID不继承任何权限/业务/签名 |
| 自锁、并发删两个管理员、锁等待中撤权、审计失败 | 不删光平台入口，无越权/部分副作用，事务失败全回滚 |
| 切组织、晚响应、原未知请求、匿名/供应商越范围 | 目标与actor明确，旧请求不能污染新scope或误删，合法范围仍可操作 |
