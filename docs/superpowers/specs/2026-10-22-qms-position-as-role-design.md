# REQ-0024 岗位即角色与用户任职授权设计

## 1. 来源与生效范围

2026-10-22，负责人明确“岗位就是角色”，要求修正飞书需求后继续。REQ-0024 的实际记录为 `reczz28QHcHW1mL3`，本次回读 revision 284、P0／开发中。该直接授权接续本地设计、开发与验证；常规 Issue／PR 使用交付流程持续授权，不自动包含合并、发布、破坏性历史迁移或人工验收。

本设计取代 REQ-0024 旧初稿的“岗位与独立角色多对多配置”方向。不追改 REQ-0022／0023 的历史验收事实。关联 [Issue #62](https://github.com/JasonShu0722/QMS-2.0/issues/62)，实施与证据见[计划](../plans/2026-10-22-qms-position-as-role.md)。

## 2. 已核对事实与方案选择

- `OrganizationService` 已有部门、岗位、任职、岗位角色映射和安全版本失效机制；`effectiveRoleGrants` 与 `effectiveRoleMembershipSql` 统一覆盖直接角色和有效任职来源。
- `AdminUserService.create` 与 `AdminUserBatchService.create` 分别写入账号，均未接入岗位；批量行映射与摘要会丢弃未显式列出的字段。
- `SupplierAccountIdentityService` 使用 `CreateAdminUserDto` 验证并赋固定门户角色，不能把内部岗位必填不加区分地施加于供应商。
- 流程固定版本 JSON 的 `roleCode`、通知与升级候选消费现有角色代码；删除／改名历史角色或替换旧映射会影响人员处理资格，即使权限码并集相同也不等价。
- 只隐藏角色页面不能阻止旧角色更新、复制、直接分配和映射 API 改写岗位授权。资源封禁还必须覆盖幂等重放前的 `authorizeResource`，不能仅放事务工作回调。

比较：直接改成 `PositionPermission` 会新增第二条授权链并重写流程／安全消费者；只给页面改名仍是两个业务对象；保留内部角色存储但标记唯一岗位归属，可以复用既有鉴权与安全链。采用第三种最小兼容方案，不新增依赖或异步授权重算任务。

## 3. 统一业务关系

```text
组织 → 部门 → 岗位（角色）→ 权限
                 ↑
              用户任职
```

管理员创建岗位及编辑其权限，不再创建独立角色再绑定岗位。多人可任同岗；兼岗沿用现有多任职，权限按来源取并集。不新增主岗／副岗，不另存一份用户部门，不从上级组织推导跨组织权限。

普通新内部用户至少选择一个有效岗位。空权限岗位允许任职和建号，但必须显示“该岗位未配置系统权限”，且实际不授予任何默认业务权限。这是保持现有允许空权限对象的最小兼容规则，不因无权限自动给基础角色，不再追问“未绑定角色的岗位”这个双对象问题。移除全部任职仍允许用于离岗与权限清理，不能把建号必填扩展为历史用户必须补岗才能登录。

## 4. 内部存储与历史兼容

### 4.1 唯一归属

在现有 `PositionRole` 新增 `isCanonical`，历史默认 `false`。数据库局部唯一索引约束每个岗位、每个内部角色至多一个 canonical 关联。沿用既有同组织复合外键，不再同时存一份 `Position.roleId`。

新内部岗位由同一事务自动创建一个内部角色及 canonical 关联。角色代码使用稳定机器标识，不依名称推断；岗位名称变更同步内部名称，角色代码不变。Position.name 最大200而Role.name最大150，内部角色名按Unicode码点截取岗位名前150字符，业务展示始终使用完整岗位名，不反向缩短岗位；覆盖150/151/200字符创建及改名边界。客户端不传内部 roleId。新岗位权限和 MFA 要求在岗位接口维护；权限存于其唯一内部 `RolePermission`，不另建第二份岗位权限表。

唯一索引不能阻止 canonical role 被非 canonical 关联或直接分配。服务必须检查角色在任意岗位的 canonical 归属，拒绝其独立更新／删除／复制、直接分配及旧映射 API 绑定；对已统一岗位的旧映射变更也拒绝。正常授权检查与资源归属检查在新执行和幂等重放前均成立。

空权限canonical依然是可能用于流程roleCode约束的岗位身份。对其任职、停用/启用和改变部门仍沿用“存在角色来源”时的角色读取／授予校验，不按权限码为空豁免。结构维护人员可建空岗位，但无上述授权不能为其任职或进行影响资格的变更；界面需说明权限不足，不以提升全体管理员权限掩盖拒绝路径。

### 4.2 存量不自动改权

新增标记迁移不创建／删除 `UserRole`，不删除旧 `PositionRole`、不合并旧角色、不重写流程固定版本。原始 `roleCode` 和来源继续参与有效鉴权。供应商固定门户角色、组织治理引导和系统恢复账号保留现有语义。

旧岗位的历史权限在统一入口单列为只读“历史兼容授权”，与可编辑的岗位自有权限清晰区分，预览与有效权限必须包含两者。不得把二者并集画成可任意取消的矩阵；取消岗位自有某权限但历史来源仍存在时，明确其仍保留。

未有 canonical 关联的旧岗位可在显式保存自有权限时初始化空的唯一归属再写入；不在只读请求中写数据库，不自动复制旧角色全部权限。该过程增加的是明确提交的自有权限，不删除旧来源。

历史整体转换是本需求中的独立迁移检查点：先产出组织／岗位／角色／直接授权／流程引用与有效人员的只读差异清单，按精确 ID 明确转换；角色被多个岗位／直接用户／固定流程共用时禁止猜测拆并。未经批准不执行破坏性转换，不能把“新链路已实现”当作历史迁移全部完成。

## 5. 服务与契约

### 5.1 岗位权限

在组织公开服务增加岗位权限读写入口，DTO 返回岗位自有权限、MFA、授权版本、历史兼容角色与当前有效任职人数。写入需要结构维护、角色读写及授予所需能力，校验权限目录、操作者授予上限、供应商白名单、最近认证与自锁保护。授权版本及权限基线必须 CAS；角色权限变更锁定相同资源、影响全部有效任职人员、安全版本与重置凭证，失败连同审计回滚。

相关角色／矩阵旧入口不提供 canonical role 独立写路径。新普通内部角色create/copy与直接assign入口在服务端收敛为受控拒绝，遗留角色的普通更新／删除／映射更改也冻结为只读；不是只隐藏菜单。内部可信供应商开通／组织治理引导不走这些通用写接口，保留其受控服务和运维恢复路径；不设置可由客户端绕过的“兼容模式”开关。冻结规则覆盖幂等回放；迁移工具如需修改历史引用，须独立授权、逐ID清单与专用事务，不恢复通用随意写入口。内部管理导航以岗位授权为主。流程设计中岗位对应 canonical role 的稳定代码可继续使用，历史 roleCode 单列兼容，不改已发布版本。

### 5.2 选择与预览

创建表单按主组织加载部门分组岗位，切组织清空旧值并丢弃迟到响应。新建、兼岗和调岗使用公开授权预览，服务只接受目标组织、岗位 ID 及可选目标用户；操作者无任职管理／目标用户读取权限时不可查看他人授权。

预览返回每个岗位的结构版本、映射版本、相关角色权限／MFA基线或等价有界签名。提交在事务锁后重新比较完整基线，包括历史来源变化；仅比较 `roleVersion` 不足以检测独立旧角色权限变化。任一变化返回受控 409 并保留草稿，不能静默授予预览后增加的权限。提交端和服务端都有限长及唯一性校验，不信任客户端预览中的权限码。

### 5.3 单个与批量建号

内部 DTO 分支要求非空岗位选择和预览基线，供应商专用开通分支不要求内部岗位。账号、任职、审计及幂等回执在同一事务内完成；复用组织模块公开事务入口，不能调用会另起事务的任职替换方法凑原子性。新增模块依赖同步治理白名单并检查循环。

批量输入保留原 `@Allow` 原始行及逐行验证语义，显式把岗位与基线纳入行归一化及请求摘要。网页新版模板增加岗位代码列，多个岗位采用明确分隔规则；代码精确匹配当前组织，不按岗位名猜测。旧三列表格缺岗位时明确要求使用新模板，不静默建无岗位账号；旧内部 HTTP 输入无岗位返回受控字段／逐行错误。

新请求使用含岗位与基线的完整新摘要；旧无岗位payload仅在已存在batch且旧归一化摘要精确匹配该batch时读取历史回执，不修改摘要、不补任职。旧批次已成功行仍投影原事实；未完成行按新规则记缺岗错误，不继续无岗写入。同key改变岗位仍拒绝，不对任意新请求同时接受一个忽略岗位的新旧摘要。覆盖升级前全部成功及部分成功batch的重放测试；秘密仍从当前受保护状态投影而非旧回执返回。

批量每行账号与任职原子提交，岗位／权限错误回滚该行并产生安全错误码，后续行可继续；认证失效、会话／组织拒绝不能吞成普通行错误后继续写。临时密码、行号、已提交事实和重放机制保持原边界，不能把秘密写入日志／Git／回执元数据。

### 5.4 用户与调岗

用户列表投影有界的部门／岗位摘要，避免逐行调用导致 N+1；详情查看任职和有效权限来源。调岗显示新增、撤销及仍保留来源，沿用现任职 CAS，额外校验岗位授权预览；自改权限成功后会话失效按已提交结果导航，不因刷新 401 误报保存失败并重复提交。

本人摘要可复用计算但不能作为新建预览或任意用户授权查询接口。普通内部用户不再呈现“再分配独立角色”步骤，历史来源明确只读；对通用旧接口的兼容和安全收敛须同时验证，不只隐藏按钮。

## 6. 前端与验证

沿用 Ant Design、生成契约、语言／主题、请求、未保存保护和焦点机制。创建表单为基本资料、组织任职、权限预览三区，不新增向导／框架。支持组织切换、加载、空态、无权限、409保草稿、失败重试、保存中关闭保护、中文／英文、深浅主题和 390／1024／1440 宽度。

真实一次性 PostgreSQL 覆盖唯一归属／跨组织约束、回滚、允许／拒绝、幂等重放资源封禁、旧／新来源并存、CAS、MFA、自锁和安全版本。真实流程／Worker验证 canonical 与历史 roleCode 的候选／动作资格，不能仅比较权限码。浏览器验证建号即任职、批量逐行、改岗位权限、调岗及 401／403链路。不得连接 55440 或以 Mock／SQLite／Skip 充当所需证据。

规格、实现、CI、部署、历史迁移与人工验收分别记录。完整验收及授权检查点以[交付流程](../../../qms-2.0/docs/DELIVERY-MAINTENANCE-PROCESS.md)为准。
