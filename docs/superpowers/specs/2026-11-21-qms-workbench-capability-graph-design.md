# QMS 工作台功能图谱设计评审稿

2026-11-21（台北时间）。以 `main` 的 `f7e182c8da4fb7ee520a8aa8ba5289e4586e2f6a`（V0.0.64 源码基线）为盘点起点。交付范围、入口清单和验收检查点见[实施策划](../plans/2026-11-21-qms-workbench-capability-graph.md)。

## 1. 功能覆盖

图谱放在内部工作台。所有内部用户都能浏览完整图谱、搜索功能、了解联动和查阅对应操作文档。负责人可按领域核对范围、进度与待验收事项。首发必须覆盖全部正式业务和管理入口、供应商门户、已确认的无菜单平台能力，以及已知的占位入口。登记批准纳入图谱的未来构想。

- 用稳定的 `capabilityId` 表示可独立说明、授权或验收的能力。多个路径指向同一能力时登记别名。同一个页面里，角色、进展或交付边界不同的主链拆成不同节点。例如“供应商质量资料”拆为内部资料审核、门户资料提交。批量导入、审批、下发、回写等独立交付动作按此口径登记。
- 每个正式入口至少映射一个能力。展开子页签、路由模板、详情入口、关键动作及其 API 或 Worker 链路。无页面的正式能力补记调用者和触发方式。旧兼容路由映射到正式节点，原型、开发预览和通配跳转在清单登记排除理由。
- 领域归属和能力名称以正式导航、页面／页签标题、操作名称或权威业务规格为准，并在目录保留来源；搜索可保留简称和旧名。分开列“客户质量”与“新品质量”、“问题中心”与“审核管理”；“质量分析”只纳入正式归属该板块的功能，“三坐标检测”归“检测管理”。不将样板临时合集名称当作产品板块。
- 每个节点登记领域、入口和别名、适用岗位、业务权限要求、功能简介、策划简介、使用文档、进度与维护责任。对全体内部用户发布的内容只包含介绍和指引，内部技术证据仍留在原有受控位置。
- 入口覆盖和关系覆盖分别验收：每个正式入口都要入图，但没有直接业务联动的能力可不连线。同领域、同导航、共用平台服务，或同受组织、岗位、权限约束，都不是建立连线的理由。

### 联动关系的收录与展示

| 收录范围 | 何时画线 | 方向与示例 |
| --- | --- | --- |
| 管理端 → 业务端 | 某项主数据、发布配置或接入规则被具体业务动作直接读取、匹配或执行，并影响业务字段、准入条件或产物。 | 提供方 → 消费方。如“工序主数据 → 不良品台账”，说明工序如何匹配、何时补齐板块以及已落账结果何时不变。组织权限仍是入口与操作的约束，只在详情和指南说明，不向全站画线。 |
| 业务上下游 | 有来源引用、字段传递、派生单据、状态回写或能说明产物的业务交接。 | 来源事实或产物 → 使用方；即使操作从下游发起选择，仍按数据方向画。如“不良品台账 → 新品同源8D”，在连线说明里明确操作发生于新品侧。只有实际存在反向写回时才另画反向边；能点回来源不是写回。 |

- 首发必须画出所有经核实的直接数据来源关系，包括 API 接收与入库、主数据匹配、业务事实引用、单据派生或回写，以及有真实来源的指标或报表取数。不因两端同属管理端或同一业务板块而省略。独立来源或目标分别画线；依赖配置的已实现路径照样可查看，说明启用条件，不把可接入说成已生效。
- 例如分别画出「API入库衔接 → 工序主数据」和「API入库衔接 → 不良品台账」。点击连线说明各自的来源、字段映射、触发方式和入库结果。在「不良品台账」同时能看到「工序主数据 → 不良品台账」，区分不良事实的直接入账与工序板块匹配。不得用间接路径替代任一直接连线，也不暗示所有记录都来自 API。
- 同一份数据经过中间能力时，逐段登记直接交互，不另画只有传递关系的捷径。共享索引或详情页不代替「不良品台账 → 制程问题跟进」这条业务关系；共用页面作为导航信息说明，只有独立的直接数据联动才另画。
- 每条关系用稳定的 `relationId` 引用两端能力，登记类型、短名称、操作位置或触发方式、前置条件、传递内容、目标结果、未触发或失败时的表现、关联指南。说明所用的是实时引用、保存时快照还是复制，以及变更是否会补配或回写；同一对能力有不同业务结果时才分线，不为每个字段单独建边。实现路径、证据与适用版本留在仓库维护记录，全体内部用户只看到业务说明和脱敏指南。
- 关系说明区分“已生效、需配置、待核验、规划中”，不改变节点的三态。可核验证据支持该环境已生效才标“已生效”；有明确启用或绑定前置条件的标“需配置”。源码已核实具体传递路径但尚无实际运行证据的标“待核验”，注明核验范围，不从节点上线反推关系生效。只有正式策划确认的关系才标“规划中”，默认不混入实际联动，未核实的猜测仅留在盘点底稿。图谱是已发布的说明目录，不读取实时生产配置或暴露组织级配置值。
- 全局保留完整关系目录，不要求一次铺满画布；聚焦节点时列全直接上游和下游，可按关系类型筛选、逐跳展开。搜索结果可定位到同一条边，端点侧栏从两个方向查看。不以绘制上限、折叠和筛选省略目录数据。首发基线、排除项和验收样例见[实施策划的联动盘点](../plans/2026-11-21-qms-workbench-capability-graph.md#首发联动盘点)。

## 2. 工作台交互与手册

- 初始视图采用**非环形的三维领域簇**，不按菜单顺序把板块等距围成一圈，也不把平面图整体倾斜充当三维。按正式领域做柔性聚类，利用三个方向的空间深度错开板块；让具有实际数据联动的领域自然靠近。例如 API 接入、主数据和制程质量彼此邻近，但不合并领域。布局的聚类和避让不代表业务连线，无直接关系的节点仍保留。
- 首选以稳定初始坐标、领域聚力、真实边的吸引力和节点碰撞避让布局；初次收敛后保持位置稳定，搜索、聚焦和普通筛选不让全图重新漂移。全局优先显示领域标签和跨板块关系；聚焦时突出相关节点、上下游和方向，弱化其余内容。真有多条并行关系时用轻微错位或曲线区分，不能把多条实际数据来源合成一条模糊的线。被遮挡的关系可通过搜索或侧栏直接定位。
- 支持拖动旋转、点击节点聚焦、逐跳展开与点击空白返回全局。另提供明确的“复位”按钮，一次清除搜索、选中和筛选，恢复稳定的初始全景、相机角度、缩放及右侧面板；样板同时恢复默认演示规模。拖动松手不视作点击，点击连线仍打开联动说明。默认不自动绕转；减少动态效果时保留同等操作，关闭非必要过渡。复用 QMS 主题和工作台导航，状态颜色配合文字和图例。
- 搜索覆盖完整图谱，包含名称、别名、入口、手册标题或小节、关系名称及关键词，例如 `IQC`、`来料`、`PPAP` 和 `工序自动入库`。结果按精确名称和别名优先。选择结果会展开对应区域、定位节点或高亮连线并打开详情。搜索、筛选和图谱导航也提供可键盘操作的列表路径。
- 点击节点，右侧显示基本信息、功能策划、使用指南、联动关系与状态更新时间。点击连线，右侧显示触发方式、传递内容、目标状态、失败或未启用时的处理，并允许在两个节点之间跳转。窄屏改用抽屉或纵向详情。图谱深链接绑定稳定 ID，与图谱采用相同的内部访问边界。
- 使用指南是岗位可直接照做的文档，包含适用版本、入口、岗位和配置前置、逐步操作、操作结果、常见异常和后续交接。已上线功能提供对应运行版本的手册与可授权入口。待上线功能显示候选文档和其适用版本。占位功能显示已记录的业务意图、已知缺口、预期操作和迭代进度。治理检查要求正式已上线能力有可交付手册或适用的技术操作文档。
- 能进入内部工作台的用户读取同一套完整节点、关系、搜索、计数和指引。管理页面和供应商门户的说明也可查看，无须拥有对应业务权限。打开真实业务页面、读取业务记录或执行操作仍由现有身份、岗位、组织和对象权限判定。没有入口权限时提示所需岗位，不授予访问权限。未登录用户、供应商账号及无法进入内部工作台的身份不能读取图谱。手册只使用脱敏样例，不下发业务记录、私有工单或验收证据。

### 开源参考与选型

以 [vasturiano/react-force-graph](https://github.com/vasturiano/react-force-graph) 为优先参考。上游 [README](https://github.com/vasturiano/react-force-graph/blob/master/README.md) 说明其 `react-force-graph-3d` 使用 Three.js/WebGL，支持三维力导向布局、相机控制和点线交互；仓库许可为 [MIT](https://github.com/vasturiano/react-force-graph/blob/master/LICENSE)。借鉴范围如下：

| 上游参考 | QMS 借鉴点 |
| --- | --- |
| [点选聚焦](https://vasturiano.github.io/react-force-graph/example/click-to-focus/)与 [交互 API](https://github.com/vasturiano/react-force-graph#interaction) | 借鉴相机朝向节点的过渡和空白点击事件；QMS 自行管理搜索、侧栏、返回全局和全量复位，不照搬示例相机参数。 |
| [节点避碰](https://vasturiano.github.io/react-force-graph/example/collision-detection/)与[大规模图](https://vasturiano.github.io/react-force-graph/example/large-graph/) | 用于验证三维领域簇、收敛和高密度图表现，以 QMS 全量目录和扩容数据试跑，不以示例帧率替代验收。 |
| [方向箭头](https://vasturiano.github.io/react-force-graph/example/directional-links-arrows/)、[曲线](https://vasturiano.github.io/react-force-graph/example/curved-links/)与[点线高亮](https://vasturiano.github.io/react-force-graph/example/highlight/) | 借鉴方向、并行关系区分和聚焦降噪；不按树或 DAG 整理业务数据，不用动效替代可读方向、标签或侧栏。 |

参考仓库不等于锁定依赖。实施时用同一份 QMS 数据核对布局可读性、交互、React 兼容性、包体、WebGL 支持和降级路径后再定版；若 WebGL 不可用，仍可通过搜索和关系列表读完整目录与指南。能力 ID、业务关系和状态由 QMS 目录维护，与渲染实现分离。

## 3. 节点状态判定

节点以已知证据选择主状态，用文字和颜色显示。已有详细策划、待人工验收、需要配置、待发布、停用等情况在详情中单独说明。下一版本迭代与当前基础能力分开记录。

| 主阶段 | 可据以展示的证据 |
| --- | --- |
| 构想中 | 已登记的想法、只有页面或占位，或证据不足以确认已有可操作的初版功能。已有详细方案时在右栏标“已有策划”，首轮证据缺口在维护记录列明。 |
| 开发中 | 有可查证的初版功能实现，仍未完成基础操作的运行调试与验证，或尚未取得基本功能完成的明确认可，或已认可但仍待实际发布。详情注明具体差距。仅有开工或 PR 记录不能把占位升为“开发中”。 |
| 已上线 | 现有交付流程中，负责人或授权验收人明确认可指定版本及范围的基本功能已开发完成，且该范围已发布并有记录。认可必须能追溯到基本功能的运行验证；合并或部署成功均不能单独升级节点。 |

例如 `/supplier/documents` 只是占位，标“构想中”；已有可操作初版、调试尚不完整的主链标“开发中”；同一页面内的内部审核单独按证据判定。已获认可的线上基础能力仍有效时，后续优化维持“已上线”。按实际发布版本更新规则、联动和指南；未发布迭代只在详情中说明，不覆盖当前线上指南。发布回滚、认可撤销或实际下线时，在同一交付检查点按仍有效的范围调整图谱，并注明受影响内容。

首发存量能力由负责人集中补确认。先复用覆盖当前基础能力范围且能追溯的明确认可、运行验证和发布证据；对缺认可的存量功能，在原计划或验收记录按领域汇总，只提交需补确认的能力，附版本、已验证范围及缺口。负责人可逐项或按明确范围批量确认；只更新实际确认且已发布的范围，未确认或验证不足的继续按三态证据标记，不影响全量入口入图。集中确认仅针对首发存量补证，不替代后续正常验收流程。

## 4. 随现有开发流程更新

开发负责人在现有任务计划、PR 检查和验收回填中同步维护图谱，沿用 `REQ/record_id → Issue → PR` 的出处。仓库内版本化目录保存节点、关系、状态和手册；工作台通过现有内部认证读取发布的目录。图谱状态随受审内容发布生效，不依赖后台采集 GitHub、飞书或部署数据，也不为同步新增 Worker、数据库投影、Webhook 或部署回执。业务功能的合并和发布继续遵循原流程。

| 现有检查点 | 图谱配套更新 |
| --- | --- |
| 需求策划与开工 | 在现有计划登记受影响的能力 ID。新增构想从“构想中”开始，详细策划和预期联动写入说明。开工本身不改变节点主状态。 |
| 初版可运行与 PR 检查 | 开发负责人有初版证据时更新为“开发中”。PR 同批检查入口、连线、手册和状态变更；图谱无变化时说明原因。既有治理检查校验覆盖、枚举与引用，审查人核对证据是否支持状态。 |
| 明确认可、发布与验收回填 | 现有计划或交付记录保留确认人、能力范围、版本、运行验证及发布证据。两项事实齐备后由负责人把节点更新为“已上线”。后续优化同步更新受影响规则、联动和指南，而不增加状态。回滚、下线或认可失效由同次发布处置或回填补更。 |

检查点及职责以[开发治理的图谱同步约束](../../../qms-2.0/docs/DEVELOPMENT-GOVERNANCE.md#工作台功能图谱随开发更新)为准，沿用[交付闭环](../../../qms-2.0/docs/DELIVERY-MAINTENANCE-PROCESS.md)。图谱更新可走受控的目录内容发布；如合并后未发布，工作台继续显示上一份目录版本。已确认的文档内容与业务运行版本各自注明，不用业务候选代码部署来更新进度。

## 5. 评审验收标准

1. 本次源码基线的每个业务、管理、供应商入口、已确认占位及关键共用能力有映射或有追溯依据的排除记录。覆盖门禁能在新增入口、孤立路由、无手册链接、错权限、悬空关系和缺失受影响能力映射时报告具体条目。
2. 普通内部账号和管理员检索到同样完整的节点、关系和手册。普通账号可读管理节点介绍，仍不能进入未授权的业务页面或执行操作；供应商和未登录身份不能读取图谱。回归原工作台、浅深主题、窄屏和键盘操作。
3. 用现有交付流程演练“登记构想 → 初版开发 → 明确认可与发布 → 更新图谱”的完整链。核对只有页面、证据不足、初版未完成验证、已发版未认可、已认可未发布、部分认可和回滚时的状态。核验目录变更在发布后才反映到工作台。
4. 首发逐领域核对已确认的直接关系是否全量登记，装饰性依赖和无联动入口有据可查；至少贯穿验证管理端入库／工序与台账、台账发起 8D 与制程问题跟进、供应商整改交接。验证连线方向、操作位置、正反例、两端可发现性，以及实际页面按原权限进入。生产部署、配置及人工验收分别登记，不把源码或本地测试当成生产生效证据。
5. 用全量目录与扩容数据检查默认和旋转后的视角，不得退化成固定环、平面或中心堆叠；全局可辨识正式领域，聚焦后能分辨两条 API 直接入库边与工序板块匹配边。连续搜索、切换焦点和复位不得让同一目录下的布局随机重排；WebGL 不可用时仍可从列表定位两端、关系和指南。
