# 阶段三供应商质量设计

日期：2026-09-19。授权范围：领域建模、接口、测试、非生产实现与平台业务联调。真实试点及生产发布未授权，须通过平台及阶段 2A 对应门槛。

## 1. 范围与架构

供应商质量拥有供应商业务资料、问题事实、简报及 8D 专业内容、回复修订和证据关系。内部提供创建、台账、详情和验证；供应商门户提供问题接收、整改回复、证据提交和进度查询。绩效评分、供应商审核、PPAP、采购结算及其他质量领域不在本次范围。

复用模块化单体的编号、公共问题索引、流程、账号权限、审计、Outbox 和附件；公共索引不增加供应商专业字段。选择“独立领域 + 平台事务接口”，不采用公共大表单或供应商自建流程。流程状态只有平台持有，领域保存事实和内容修订，不复制状态机。

## 2. 已确认规则与决策边界

- 问题从业务域创建，一事一号；简报升级 8D 保留编号、来源、证据和历史，不覆盖人工内容。
- 内部组织是业务拥有方，供应商企业是协作方，两者必须使用不同引用。
- 企业身份来自后端会话及服务端关系；请求中的企业 ID 不能扩大供应商范围。
- 功能权限、数据范围、节点授权必须全部满足。内部验证和关闭不能由供应商执行。
- 供应商提交的是整改内容；提交、驳回、重提、升级、验证、关闭与归档由公共运行时处理。
- 用户已确认：一单一家责任供应商，多供应商拆单；发单必选简报/8D；工程师可以升级；SLA 结合严重度配置；内部流转指定内部个人回复，外发单由供应商回复；验证人与关闭人必须分离。
- 用户授权参考 1.0 字段。通过共同基线的 Git 对象只读查看 `backend/app/schemas/scar.py`、`schemas/problem_management.py` 和 `frontend/src/views/supplier/EightDForm.vue`，未展开、执行或复制旧实现。
- 首批采用旧 SCAR 的必填物料编码（100 字符）、缺陷描述、不良正整数、严重度 LOW/MEDIUM/HIGH/CRITICAL；来料分类 STRUCTURE/ELECTRONIC 按旧 API 保持可选（旧页面要求必填，明确以 API 口径为此次起点）。标题上限 500；缺陷/回复文本增加 10000 字符技术上限。来源分类和批次作为后续领域扩展，不猜测新增必填约束。
- 简报最终回复要求原因、纠正措施及含时区完成时间；8D 最终专业回复要求问题描述、围堵、临时措施、根因、纠正措施、预防措施及供应商自验结果。自验结果不代表内部验证通过。草稿允许部分内容；过程节点提交不能错误使用最终回复校验。回复形式显式选择，不沿用旧版按低严重度自动推导简报的规则。
- 时限数值由平台配置，缺配置时不能伪造默认时限；不硬编码 D0–D8 节点、审批人及证据必填数。工程师升级通过真实功能权限和节点权限控制，不按显示角色名称判断。

## 3. 领域模型

| 模型 | 所属事实与约束 |
| --- | --- |
| SupplierBusinessProfile | 内部拥有组织与供应商企业的业务关系、业务代码及必要联系资料；组织身份继续复用 Organization，不重复维护账号企业 |
| SupplierQualityProblem | UUID、拥有组织、标题、问题描述、发现时间；物料、批次、来源与数量规则经业务确认后扩展；通过稳定 UUID 关联公共索引 |
| SupplierProblemParticipation | 一条问题只关联一家供应商；该关联及释放给供应商的时点控制协作访问，不等同全组织访问授权 |
| SupplierResponseRevision | 专业回复内容、提交人、修订号及关联平台节点/实例版本；已提交修订不原地覆盖，驳回后建立新修订 |
| SupplierEvidenceReference | 领域资源、文件 UUID、用途及内容修订；只保存引用，文件生命周期由平台拥有 |

首批以类型和纯规则实现事实输入、内外回复人约束、同版本验证与关闭职责分离、证据校验以及简报映射；本表中持久化、接口和页面交付以执行计划及 PHASE-3 证据为准，表的存在不表示实现完成。

## 4. 访问边界

内部用户仅在平台已经授权的拥有组织范围内访问。供应商仅在其会话企业与服务端问题协作关系匹配时访问，不获内部拥有组织的通用权限。跨企业 ID 猜测、未发布给供应商的内部记录、跨组织关联均拒绝。

领域资源校验只是平台功能权限与节点授权之外的一项必要条件，不自行授予角色权限。未来真实 API 权限增量包括内部问题读/创建/维护、供应商问题读/回复、内部验证及证据操作；只在后端授权、catalog、迁移、生成契约和成对允许/拒绝测试同时接入时激活目录。

## 5. 平台接口及事务约定

已核对平台工作树的 `qms-2.0/docs/PLATFORM-HANDOFF.md`（2026-09-19 实施中草案）。

- `ProblemIndexService.createFromDomain(tx, input)` 使用调用方事务；`domainCode = supplier-quality`，稳定 `sourceId` 指向领域问题 UUID。编号不得解析用于授权。
- 创建：领域事实 + 编号 + 公共索引 + 固定版本流程实例 + 审计 + Outbox 必须同一事务提交。运行时未就绪不得发布部分成功的正式创建 API。
- 动作：运行时公开 start/action 接收同一个 Prisma.TransactionClient 及仅首次执行的领域 mutation 回调。领域内容、索引及流程分别校验预期版本；任一写失败全部回滚。
- 幂等摘要包含领域 payload，按 actor、组织和请求键限定；相同请求返回原回执，不同内容 409；撤权后不能重放。并发冲突 409，客户端保留草稿并提示刷新。
- 事件 v1 使用平台 WORKFLOW_STARTED / WORKFLOW_ACTION_COMPLETED，实例 ID + 版本去重，包含拥有组织、索引、实例、流程版本、前后节点和动作。业务内容不塞入通知事件。
- 跨组织供应商节点授权未交付：需要平台接收领域授权结果并重新校验会话、功能权限和 assignment，禁止传入伪造内部组织上下文。
- 领域证据检查需要平台在授权资源边界下返回文件状态与归属；当前 FileLifecycle 无真实上传/资源鉴权闭环，不接入可下载证据。
- 错误沿用平台安全响应、traceId、409 与统一拒绝；新增领域错误码必须与共享错误目录和 Swagger 同批集成。

## 6. 首批内容输入与证据规则

内部事实输入包含已确认的单一供应商、非空标题/物料/缺陷描述、正整数数量、严重度、显式回复形式及内外回复模式。内部模式必须指定个人；外发供应商模式不允许指定内部回复人。格式归一化返回新值，不修改调用方草稿；不接受客户端 status/verifier/dueAt/组织拥有方注入。

证据校验只接受可信平台解析结果，不接受浏览器提交的状态/归属。引用必须唯一、齐全，属于目标 supplier-quality 资源，拥有组织与协作企业符合当前服务端授权；QUARANTINED/DELETED 文件不得提交。初始安全校验不指定数量必须大于零，各节点的业务必填性留待确认。

## 7. 页面与 API 分批接入

内部入口规划 `/app/supplier-quality`，门户入口规划 `/supplier/problems`；共享导航由平台协调。台账进入完整详情工作空间；表单保留 409 草稿、重复提交使用稳定幂等键；领域内容区依附公共节点，不硬编码流程进度。

API DTO 只在 Nest Swagger 定义，运行 `pnpm contracts:generate`，Web 仅从 `@qms/contracts` 导入。未接入控制器的领域内部类型不是 API 合同，不手工修改 generated/api.ts。

以下是下一批待实现的 HTTP 设计，不是当前可调用端点：

| 路由 | 功能权限增量 | 数据与事务要求 |
| --- | --- | --- |
| GET /api/v1/supplier-quality/problems | supplier-quality:problems:read | 内部授权拥有组织过滤，分页限制 100，列表不泄漏其他组织 |
| POST /api/v1/supplier-quality/problems | supplier-quality:problems:create | 单供应商事实 + 固定流程版本；Idempotency-Key、CSRF；同事务创建领域/索引/实例/审计/Outbox |
| GET /api/v1/supplier-quality/problems/:id | supplier-quality:problems:read | 内部组织过滤后读取领域详情；不可见与不存在统一 404 |
| GET /api/v1/supplier-portal/problems | supplier-quality:responses:read | 会话供应商企业 + 已释放外发单过滤；不接受扩大企业范围的请求参数 |
| GET /api/v1/supplier-portal/problems/:id | supplier-quality:responses:read | 单条记录同样检查企业、外发模式和释放状态 |
| PUT /api/v1/supplier-quality/problems/:id/response-draft | supplier-quality:responses:write | 指定内部回复人；expectedContentVersion，审计与草稿同事务 |
| PUT /api/v1/supplier-portal/problems/:id/response-draft | supplier-quality:responses:write | 供应商企业资源校验；expectedContentVersion，不能修改内部事实 |
| POST /api/v1/supplier-quality/problems/:id/actions | 领域操作权限 + 公共 workflow:act | 内部节点操作；验证/关闭还需职责分离，升级需要工程师被授予的升级权限 |
| POST /api/v1/supplier-portal/problems/:id/actions | supplier-quality:responses:write + 公共节点权限 | 只允许当前供应商回复节点可执行动作，expectedContentVersion/expectedVersion/expectedProblemVersion、幂等与同事务 |

权限代码是待协调增量，不会仅因为出现在此表而写入可授予目录。公共动作 DTO、action 名称与跨组织 permission context 采用平台最终签名；升级与附件 HTTP 入口复用平台接口，不建立平行接口实现。

数据库增量采用 UUID、timestamptz、整数版本。SupplierQualityProblem 必须有拥有组织、单一供应商引用、稳定领域 UUID 和唯一公共索引引用；回复修订对 `(problemId, revision)` 唯一，证据引用对 `(responseRevisionId, fileId)` 唯一。真实迁移需验证拥有组织是 INTERNAL、供应商组织是 SUPPLIER、内部回复人归属与状态有效，不能只凭 UUID 外键证明类型和数据范围。索引和流程写入只通过公开事务服务完成。

## 8. 验收与门槛

依次验证领域规则 → 真实 HTTP/API + PostgreSQL → 页面 → 平台联调 → 真实浏览器主链。真实链路必须覆盖创建、聚合、分派、供应商回复、内部验证、关闭归档，以及驳回重提、简报升级 8D、重复提交、并发冲突、事务回滚和 Worker 失败恢复。

每项接口同时证明允许与拒绝；使用至少两个内部组织、两个供应商企业及被撤权用户。测试替身仅作为规则测试输入，不代表会话授权、数据库、上传、Worker 或联调完成。

独立临时 PostgreSQL 55448、API 3318、Web 5188、网关 8088，Docker 项目 qms2-supplier-quality；运行前核查占用，结束销毁本任务临时资源。不得使用 55440 或其他任务的资源。日志/凭据在仓库外。真实试点须平台运行时、业务 Worker、上传、完整主链及阶段 2A D–H 对应门槛通过；不自动推送部署。

## 10. 已授权的非生产草稿子集

本轮实现供应商资料登记/查询、问题草稿 CRUD 中的创建/读取/更新以及内外回复草稿保存。实际 HTTP 与 Swagger 契约以 `supplier-quality.dto.ts` 和生成契约为准；正式发单 `POST problems` 和 actions 仍是待实现设计，不对外提供缺流程的成功结果。

内部草稿创建改用 `POST /api/v1/supplier-quality/drafts`，更新为 `PUT drafts/:id`；草稿写权限为 `supplier-quality:problems:write`，正式发单权限将在平台合入时单独确认。回复草稿和问题更新均使用单一领域 `expectedVersion`。资料目录使用 profiles:read/write；门户读/写使用 responses:read/write；不新增公共权限框架。

保存使用既有 Serializable 事务服务，领域/审计/幂等回执同事务。问题没有公共索引之前只是草稿；服务器根据 profile 派生责任供应商，不信任客户端企业或释放标记。门户仅读取关联当前供应商企业的 SUPPLIER 模式已释放记录，已结束索引状态禁止编辑。运行时接入后需按平台 ReadCommitted/行锁约定调整正式动作事务，而非复用草稿事务假装流程可用。

数据库预留正式回复修订/证据引用表，目前仅覆盖结构外键及问题级证据去重；正式修订级引用、附件资源授权和不可变性应在平台接口完成后补齐并验收。不存在通过这些表跳过平台上传/扫描/节点授权的公共端点。

页面保存失败保留输入，同内容网络重试复用幂等键，内容改变产生新键；版本冲突明确要求保留内容后重新加载。完成时间按用户设备时区填写并转为带时区的 ISO 时间提交。正式发单、提交回复、上传证据显示不可用。

## 11. 并行完善批次

用户授权清理不依赖平台的剩余工作。本批完善既有草稿能力，不增加业务状态或改变已确认规则：

- 供应商资料支持读取单条和 PUT 更新业务编码、联系人及邮箱。关联企业和拥有组织不可通过编辑变更；使用已有 version 进行 CAS，复用审计、幂等和 scopes。空联系资料可清除，冲突不丢输入，明确重新加载最新版本。
- 企业、业务资料和内部回复人选择采用服务端搜索、稳定排序分页及 selectedId 回显。单页上限 100；指定 ID 仍受相同类型/组织/有效身份约束。Web 处理加载、错误、重试、追加页及旧请求晚到，不将首批 100 条当作完整目录。
- 内部和供应商台账支持严重度、回复形式筛选；内部额外支持草稿/已发单筛选。服务端过滤与资源范围采用 AND 组合，门户不可借草稿条件读未释放记录。
- 内部事实与回复草稿同时可编辑时，保存一个表单不重置另一个尚未保存的内容。8D 字段标明供应商自验，不暗示内部验证已经通过。

验收包括真实 PG 的资料编辑/清空/重复编码/并发/跨组织/回滚/撤权重放，以及目录分页/选中值/非法查询和过滤隔离；Web 与真实浏览器验证资料编辑、远程选择、8D/内部回复、筛选及跨表单保存。未交付的修订、证据、正式流程保持平台依赖。
