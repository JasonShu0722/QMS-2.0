## 1. 目标与已确认口径

在“组织与岗位”内统一岗位、权限、用户任职及兼容授权处置，不再维护两套业务授权入口。

1. 系统管理员可设为组织直属岗位，不要求挂靠业务部门或创建虚构部门。
2. 部门/科室业务岗保留原组织及职责边界；组织直属岗不自动成为科室经理、部长或专业审核人。
3. 旧角色可迁入已有或新建岗位；不用的兼容授权可解除、角色可移除，不再被只读页面永久搁置。
4. 迁移不是复制权限后保留两条生效来源：确认范围内的旧直接授权和旧岗位映射由新任职/自有权限替代，历史来源仍可追溯。
5. 保留当前平台管理员能力，不能迁移后将执行者自己锁在系统外，也不按用户名、角色显示名猜测授权。

本设计对[岗位即角色设计](2026-10-22-qms-position-as-role-design.md)的“岗位必须在部门下”和“旧角色普通维护冻结”作定向补充：保留canonical存储与普通旧写接口拒绝，增加组织直属及受控兼容处置，不恢复独立角色随意编辑。

## 2. 已核实的实现断点

- `Position.departmentId`、创建/更新DTO及岗位表单均要求部门；有效任职ORM/SQL、岗位授予预览和目录/管理职责也依赖有效部门，不能只取消界面必填。
- 新内部岗位已自动创建唯一canonical角色，权限/MFA仍存现有Role/RolePermission；不新增一份岗位权限表。
- `AdminPage`将独立RoleAdministration固定为readOnly，旧角色HTTP写接口由`rejectIndependentWrite`主动拒绝。旧`remove`又拒绝关联用户/岗位；解除和迁移接续没有面向用户的完整入口。
- 工作流仍可使用稳定roleCode作实际成员约束；权限集合相等不代表身份资格相等，不能只比较按钮权限。

## 3. 岗位归属

沿用Position.organizationId，允许departmentId为空，空值明确表示“组织直属”，不是待配置或失效部门。页面提供“组织直属 / 部门科室”选择，不另存一份冗余归属类型。

- 组织直属：组织有效、岗位有效、任职在有效期内即可提供岗位自有功能权限；不得要求临时部门。
- 部门科室：沿原规则要求同组织有效部门，部门停用/删除/待配置时对应岗位资格失效。
- `configurationRequired=true`、deletedAt或停用仍显式拒绝；不能把失效部门清空后假装成直属岗复活。
- 向直属/部门切换属于显式岗位调整，纳入预览、版本、影响人员和撤权复验；删除部门不会隐式把其岗位改成直属。
- 流程中要求责任科室、经理绑定或部长分管的候选只接受满足这些结构要求的真实业务任职；platform marker不是业务职责通行证。

## 4. 兼容角色处置

### 4.1 入口与处置选择

取消平台管理独立“历史授权”顶层页；在“组织与岗位”内提供“兼容授权迁移/清理”。用户/岗位详情共用只读“授权来源”，区分岗位自有、兼容岗位映射、兼容直接授权、系统初始化来源及已经解除的历史。

每条兼容角色展示原组织/角色ID、代码/名称、权限/MFA、直接账号、岗位映射、有效/未来任职及流程引用摘要；同名不合并。提供：迁入已有岗位、迁入新岗位、解除并移除。未使用的角色可直接确认移除；有关联的允许在同次确认中转岗或解除，不要求到另一只读页面拆依赖。

“移除”是退出当前可配置/授权集合；没有历史引用的可按既有删除语义清除，存在历史/固定版本引用的保留稳定UUID与归档事实，普通目录不再将其当活跃角色。审计与旧批准/签章不删除。

### 4.2 预览与原子执行

预览固定精确角色、目标组织/岗位、受影响用户、各直接/映射来源、有效期、roleVersion/安全版本、权限/MFA与流程角色资格。列明新增/保留/解除及非本次范围的来源，不能按计数相同忽略来源替换。

执行由真实已授权actor、近期认证、CSRF、幂等和预览摘要保护；按固定顺序锁资源后重采，漂移拒绝并要求重新预览。同事务建立/调整岗位自有权限及任职、解除确认替代的旧来源、归档角色/来源事实、推进相关版本、撤旧会话/凭据并记审计；任一步失败全部回滚。存续账号保留已绑定MFA及锁定状态，不能再次误用永久用户删除清理。

迁入已有岗位时必须显示该岗原权限、MFA、全部任职人员及扩散影响；不能为了迁一个旧角色而静默提升原岗位的其他人。多岗位/共享角色需明确每个来源去向，默认不扩大迁移集合。

### 4.3 稳定角色与平台管理员

- `QMS_ADMIN`迁入组织直属系统管理员岗位，保留其平台marker、MFA要求和实际任职来源。优先将可一对一承接的原角色作为目标岗位canonical后端身份，保留角色ID/code，不创建可重复直接分配的第二身份。
- 一对多/已有canonical岗位或固定工作流引用不能猜测合并。只读展示引用，选择能保留旧roleCode资格的映射或指定独立承接岗位；不重写已发布流程版本或旧审批快照。权限和角色资格两者都要验证。
- 操作者最后一条有效平台管理来源必须有事务内等价有效替代；不允许先撤后补造成自锁。普通同名管理员不得获得marker，供应商门户角色不能迁入内部管理岗。
- `ORGANIZATION_GOVERNOR`明确标注系统初始化兼容来源，可迁入组织管理岗位，也可解除不再需要的授权；不强制所有组织都建立同名岗，不因名称猜测清理其他记录。初始化/旧幂等回放不得把已移除来源重新激活。
- `test`等无用户/岗位/有效流程依赖的兼容角色可直接移除；数量与状态必须以实际预览为准，不凭截图预先操作。

## 5. 不做的事情

不新建权限引擎、角色管理顶层页或另一套用户部门；不全量自动转换历史角色，不在迁移SQL中批量赋权/删除用户授权，不自动创建各科室管理员；不把平台能力变成真实业务代审批。不迁移供应商企业、不调整业务事实/指标/IMS/AI，不关闭旧Issue/REQ或恢复夜间自动化。

## 6. 验收与停止条件

| 场景 | 必须结果 |
| --- | --- |
| 组织直属系统管理员创建/任职/切组织/到期撤销 | 无部门也正常生效，ORM/SQL/菜单/API一致；到期后实际拒绝 |
| 普通部门岗位与直属业务审批候选 | 原部门保护保持；直属管理员不因功能全量而入经理/部长/专业候选 |
| QMS_ADMIN迁移 | 前后平台范围与角色资格一致；旧直接来源解除、新任职生效，重新登录仍可管理 |
| 已有岗位另有成员/其他来源 | 预览准确显示扩散影响；未确认来源/成员不改权、不全局撤同用户其他资格 |
| 兼容角色移除 | 有关联可同次明确解除/转岗；历史/固定版本可追溯，普通目录消失，旧回执不能复活 |
| 并发改权/任职到期/同数来源替换/审计失败 | 预览失效或全回滚，无部分迁移/失权，旧批准记录不改 |
| 保存中/未知结果/401403/409/切组织迟到 | 按既有保护保原请求、清敏、显式重新预览，不在新scope误迁移 |

完整范围完成本地规格后独立质量、真实一次性PG/必要Worker及浏览器验证后才到PR检查点。代码发布与生产角色转换分开：生产按精确预览逐批确认，旧角色不在本次规划阶段被删除。
