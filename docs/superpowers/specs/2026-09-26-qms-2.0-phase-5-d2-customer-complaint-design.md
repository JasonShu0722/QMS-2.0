## 1. 已有能力与确切缺口

| 环节 | 当前源码事实 | D2 缺口 |
| --- | --- | --- |
| 登记 | `CustomerQualityService.createComplaint`、`POST /api/v1/customer-quality/complaints` 已支持 0KM/售后、客户、缺陷、VIN/里程/购车日期、严重度政策快照、外部来源标识、幂等；D4 支持 Excel 导入与逐行结果。 | Web 只有列表、详情和导入，没有人工登记表单；导入后仍需分诊。 |
| 分类和责任 | `complaint_type` 只区分 0KM/售后；实物处置的 `responsibility` 是自由文本。组织模型已有 `departments`、`users`。 | 无业务分类、责任部门和经办人字段；无同组织、在职、部门有效性校验或改派历史。 |
| 进度 | `customer_quality_complaints.status` 声明 `OPEN/IN_ANALYSIS/RESOLVED/ARCHIVED`；实物处置和解析有各自版本历史。 | 除 `archiveComplaint` 外，服务没有写客诉处理状态的操作；缺少分诊、进展、解决、复核事件和时间线。实物分支状态不能代表客户投诉处理进度。 |
| 关闭 | 当前 `archiveComplaint` 可把任意未归档客诉直接改为 `ARCHIVED`。 | 没有 `CLOSED`、解决说明、复核、关闭前置条件和重开规则；归档会绕过处理闭环。 |
| 正式问题 | `CustomerIssueService.issue` 可从一条或多条客诉发起 `BRIEF/EIGHT_D`，绑定发布的 Workflow，要求验证节点和独立验证关闭节点；来源增删及历史已有服务。 | 客诉页面没有发单和问题回看主链；台账解决/关闭未与当前有效关联问题的状态互锁。不能把客诉状态当成 8D 工作流状态。 |
| 附件与外部来源 | 平台 `file_objects`、对象存储、扫描与 Worker 已存在；客诉外部来源只记 `ERP/SAP/IMS` 键和 `PENDING_VERIFICATION`。 | 处理证据未绑定客诉事件；外部接口字段、认证、样本和联调未确认。 |

现有真实 PostgreSQL 测试覆盖登记、导入、实物分支、幂等和隔离；真实浏览器仅覆盖 D4 导入。不得把这些证据解释为 D2 关闭链已通过。

## 2. 方案与边界

选择在现有客诉台账上增加分类、责任归属和不可变处理事件，当前状态仍由 `customer_quality_complaints` 投影。另建一套客户投诉 Workflow 会复制平台的任务、验证和关闭规则；仅用现有自由文本 `responsibility` 又无法做组织校验、进度和复核，因此均不采用。

客诉是来源事实和客户侧处理承诺；正式问题是跨部门原因分析、简报/8D、审批、验证与归档。登记、导入或分诊不自动发起正式问题。若严重度政策快照明确要求正式发单，解决前必须存在当前有效的正式问题关联；政策没有该要求时，允许通过台账完成无需解析的简单客诉。所有已关联的当前有效问题必须在平台内完成关闭，才允许该客诉关闭。历史上已移除的关联保留审计，但不参与当前关闭门禁。

## 3. 数据模型与迁移

在 `customer_quality_complaints` 增加以下可空列，保证已登记历史记录可迁移，不能回填猜测事实：

| 列 | 类型与约束 | 说明 |
| --- | --- | --- |
| `category` | `varchar(32)`，`PRODUCT_QUALITY/DELIVERY/SERVICE/OTHER` | 与现有 `complaint_type` 独立；`OTHER` 需 `category_note`。 |
| `category_note` | `varchar(200)`，可空 | 只有 `OTHER` 可填写。 |
| `responsible_department_id` | `uuid`，同组织复合外键 `departments(organization_id,id)` | 责任部门；分诊时必须为 `ACTIVE`。 |
| `owner_user_id` | `uuid`，同组织用户约束 | 当前经办人；分诊时必须为在职内部用户。 |
| `resolution_summary` | `text`，可空 | 解决时填写，长度 1–10000。 |
| `resolved_at`、`resolved_by_id` | `timestamptz(3)`、`uuid` | 解决决定的时间和人员。 |
| `closed_at`、`closed_by_id`、`closure_note` | 时间、人员、`text` | 独立复核关闭证据；重开保留历史事件并清空当前投影。 |

扩展 `status` CHECK 为 `OPEN/IN_ANALYSIS/RESOLVED/CLOSED/ARCHIVED`。新增 `customer_quality_complaint_events`：`id, organization_id, complaint_id, seq, event_type, from_status, to_status, note, category, responsible_department_id, owner_user_id, evidence_file_object_id, actor_user_id, created_at`。`(organization_id,complaint_id,seq)` 唯一、同组织复合外键、事件只插入不修改；事件和投诉版本在同一数据库事务更新。`evidence_file_object_id` 可空，提交时必须是同组织、`resourceType=CustomerComplaint`、`resourceId=complaintId`、未删除且扫描通过的 `file_objects`。事件读取按 `seq` 升序，详情返回当前投影和时间线；审计日志继续记录操作、版本和 trace，不把历史只藏在审计元数据里。

新迁移只增量修改当前表和 CHECK，不修改已执行的 `20260924030000_customer_quality_ledger`；原有 `OPEN` 记录保持未分类、未分配，归档记录保持历史状态。迁移前后在一次性 PostgreSQL 验证行数、约束、索引及回滚预案；回滚优先使用数据库快照恢复，不能删除处理事件保留的证据。

## 4. 状态、命令与关闭规则

| 命令 | 允许原状态 → 新状态 | 必填与守卫 |
| --- | --- | --- |
| 分诊或改派 | `OPEN → IN_ANALYSIS`；`IN_ANALYSIS → IN_ANALYSIS` | 分类、有效同组织部门、在职同组织经办人、说明；生成 `TRIAGED/REASSIGNED` 事件。已归档、已关闭禁止改派。 |
| 记录进展 | `IN_ANALYSIS → IN_ANALYSIS` | 1–10000 字进展说明；可选已扫描证据；生成 `PROGRESS_RECORDED`，不允许客户端直接报“完成百分比”。 |
| 解决 | `IN_ANALYSIS → RESOLVED` | 分类、责任、解决说明；要求的实物解析为 `COMPLETED`，或 `MISSING` 且有明确缺失理由及可接受处理决定；需退件时实物处置 `CLOSED`；政策要求发单时有有效问题关联。 |
| 复核关闭 | `RESOLVED → CLOSED` | 不同于 `resolved_by_id` 的有权复核人、关闭说明；当前有效关联的所有问题状态为 `CLOSED` 或 `ARCHIVED`，且其 Workflow 已完成独立验证。审查关系和状态须在事务内重新读取并锁定，不能依赖页面缓存。 |
| 重开 | `RESOLVED/CLOSED → IN_ANALYSIS` | 必填理由和有效责任归属；插入 `REOPENED`，清空当前解决/关闭投影，旧事件不变。若关联问题已关闭，沿用问题中心的重新发单/来源关联能力，不篡改旧 Workflow。 |
| 归档 | `CLOSED → ARCHIVED` | 改造现有归档 API 以强制状态前置条件；保留原有详情和时间线可读。 |

所有命令携带 `expectedVersion`、`Idempotency-Key`、CSRF，使用现有 `AdminMutationService` 做同键重放与不同载荷冲突；缺少必填字段为 400，跨组织/撤权为 403 或不可发现的 404，过期版本和非法状态为 409。先锁定客诉，再检查关联、附件和责任对象；事务失败不得留下事件、版本增长或部分审计。已归档记录只可读，不可再改写处置、解析、分类和进度。

## 5. 权限与接口

读取列表、详情、时间线及关联问题使用 `customer-quality:complaints:read`；分诊、改派、进展、解决、重开和归档使用现有 `customer-quality:complaints:write`。复核关闭除该写权限外，要求与解决人不同；平台正式问题操作继续走 Workflow 当前节点、任务归属、`workflow:*` 等原有权限，不因客诉写权限扩大。操作均限定内部账号和当前组织；撤权后的同键重试也不得回放成功结果。

API 采用现有 `/api/v1/customer-quality`：新增 `PUT complaints/:id/triage`、`POST complaints/:id/progress`、`PUT complaints/:id/resolve`、`PUT complaints/:id/close`、`PUT complaints/:id/reopen`、`GET complaints/:id/events`；沿用 `POST complaints`、`POST complaints/import`、`GET complaints/:id/issues`、`POST issues`、问题工作区和附件服务。Controller 只做契约和授权，规则在客诉领域服务。所有新 DTO 用 Nest Swagger 生成 `@qms/contracts`，Web 禁止自定义并行 DTO。

Web 在现有 `/app/customer-quality` 提供人工登记、分类和责任选择、状态与进度时间线、实物处置/解析、解决/关闭/重开、正式问题链接；提交后重新取详情和权限。只读用户只看有权数据，无写入控件；403 清除旧敏感详情，409 展示最新版本并要求重试，异步切换投诉时不能把上一条详情显示到下一条。窄屏、空态、加载、失败重试、键盘焦点遵守前端统一规范。

## 6. 外部接口和附件边界

ERP/SAP/IMS 仍只保留 `externalSourceSystem/externalRecordKey/sourceObservedAt` 与待核实状态。启用任一真实来源前，须冻结字段映射、认证、推送/拉取方向、样本、外部幂等键、批次和时区、失败重试及审计；未确认时人工登记与 Excel 导入独立可用，验收记录外部集成“未启用”。不制造模拟同步成功结果。邮件或客户通知不随状态变更直接发送；如后续要求通知，由 Worker/outbox 驱动并独立验收。

证据经现有文件服务上传至一次性对象存储，由真实扫描服务和 Worker 处理；隔离或扫描失败文件不能成为解决/关闭依据。事件只保存已授权的文件对象引用，不保存本地路径、密钥或二进制。D3 客户索赔、D8 批次追溯、8D 专业章节强化和严重度工作日 SLA 不在 D2 重复实现，分别遵循对应阶段计划。

## 7. 验收定义

用全新一次性 PostgreSQL 18、对象存储、ClamAV、Worker、网关和 Chromium 验证：人工登记或 D4 导入→分诊→改派/进展→实物处理或解析→解决→独立复核关闭→归档；再跑正式问题简报/8D 分支，验证未关闭问题阻止客诉关闭、Workflow 关闭后成功。覆盖跨组织、只读、撤权后的重试、相同键重放、不同载荷/过期版本 409、无效部门/经办人、扫描失败证据、重开与历史、事务回滚。实际 PASS/FAIL、命令、资源标识与限制写入 `qms-2.0/docs/PHASE-5.md`；缺少任一真实前置条件必须失败，不以 Mock/SQLite/Skip 代替。
