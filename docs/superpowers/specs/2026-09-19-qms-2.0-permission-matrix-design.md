# QMS 2.0 分板块权限矩阵补充设计

## 授权与范围

用户已批准继续补齐 C 切片中“板块 → 模块 → 操作”的权限目录和配置体验。基线为 `524da124`；复用 NTFS 工作树及完整依赖，在 `codex/qms-2-permission-matrix` 实现。E 盘主项目只在验收后同步，不在那里重装依赖。使用 subagent-driven-development，单一实现写者、每任务红绿验证与提交、规格审查后质量审查，反馈经主代理验证后交新修复代理。

归档只读参考，不复制旧实现。实现限定 `qms-2.0/`，根目录仅治理文档。此补充不启动 D–H、供应商领域或其他专业领域业务，也不把流程节点权限混入普通角色授权。

## 方案选择

采用 API 持有的静态权限目录元数据与现有 PostgreSQL Permission/RolePermission 合并。相比前端按字符串猜分组，它有唯一契约；相比新增可编辑权限树数据库，它不引入运行时自造权限入口。角色成员和组织范围仍使用现有模型。

目录按平台功能、供应商质量、制程质量、客户质量、新品质量、审核管理、系统管理分组。平台登记现有问题查询、受控流程管理和工作台权限；系统登记组织目录、当前权限上下文、用户管理、角色管理。工作台查看是既有预留标识，不宣称存在独立工作台 API 的拦截证据。现有 workflow:manage 真实覆盖创建/编辑/校验/发布/复制，本轮明确作为一个“管理”操作保留，不伪拆出未验证的流程授权。

未来业务板块及其模块只有 planned 状态与中文名称，没有可提交权限代码、数据库 Permission 或生产业务入口；供应商模块列供应商管理、绩效、审核、PPAP、整改，其他域按总设计列主模块。未实现的删除/导出/审批能力不制造复选框。代码中登记、迁移中建立且被当前账号持有的有效权限才可授予；伪造 planned/未知代码即使手工存在数据库也必须拒绝。

## 细粒度账号授权

保留 `account:users:read`、`account:roles:read`，新增：

| 模块 | 权限后缀 | 含义 |
| --- | --- | --- |
| account:users | create | 创建用户 |
| account:users | update | 编辑邮箱 |
| account:users | status | 启用/停用 |
| account:users | transfer | 修改主组织或账号类型 |
| account:users | reset | 签发一次性重置凭证 |
| account:roles | create | 创建和复制角色 |
| account:roles | update | 修改角色名称或权限 |
| account:roles | delete | 删除未使用角色 |
| account:roles | assign | 分配用户角色 |

用户 PATCH 根据实际提交字段确定所有必需权限：email→update、status→status、organizationId/accountType→transfer。混合请求全部满足才执行；空 PATCH 需 update。保留 UUID/组织范围验证，供应商只能本企业。服务事务在幂等回放前重新校验完整权限集合；目标用户各已分配组织的子集保护继续成立，跨组织迁移两端都需 transfer。不能通过持有 update 停用、迁移或重置账号。

保留 CSRF、Serializable、事务审计、成功重放和异内容 409、全局角色保护、会话及重置凭证失效规则。自锁保护包含全部 11 个账号管理权限。矩阵写入仍走角色 PATCH，不增加绕开服务的批量写入口。

角色权限修改携带读取时的 `expectedPermissionCodes`；提交 permissionCodes 时必须提供该基线，按集合比较。当前集合不同返回受控 409，回滚全部修改；仅改角色名不提交这两个字段。前端保留草稿并提示重新加载。重放仍先校验权限，不因旧成功响应绕过撤权。

## 迁移和兼容边界

新增 PostgreSQL 迁移原子建立九个写权限，将每个旧 users:manage 角色关联展开为五项、roles:manage 展开为四项，去重后移除两种旧 manage 关联及权限记录。包含全局角色，保持 UserRole 和已有 read 授权不变，不补授 read。同步种子及夹具，不允许 seed 重新写回 manage，也不保留 manage OR 新权限运行时后门。历史审计原文保留；权限目录和当前会话上下文只反映现行授权。升级应用与迁移应协调完成。

## API 与页面

新增 `GET /api/v1/admin/permission-catalog?organizationId=...`，要求角色读取权限和目标组织范围，返回有类型的组、模块、操作、状态与可授予标记。静态目录名称、顺序、状态由 API 提供；现有平铺 permissions 端点保留，所有 Web 类型仅使用生成 contracts。

权限矩阵改为角色选择、板块筛选、模块与操作复选框。支持按模块名称/权限名称搜索、模块内已可授予项全选/清空、已修改计数、保存/重置。批量选择不得加入 disabled 或 planned 项，不改变未显示组的授权。未持有角色 update 的账号只读；管理员无权授予的项禁用。全局角色只读。无变化不 PATCH，保存仅发送权限与基线；切换角色/组织前有未保存修改应明确确认放弃，不静默丢弃。

角色创建/编辑也复用分组权限选择器。用户页按细权限分别展示创建、编辑、启停、迁移字段、重置和分配操作；组织候选按 create/transfer 区分，不把写权限自动当读取权限。组织目录、导航与自锁列表同步新权限。

## 验收

真实 PostgreSQL 验证旧角色迁移与授权连续性、不补授 read、各独立权限的允许和互斥拒绝、混合 PATCH 原子拒绝、撤权后幂等回放拒绝、两端迁移、子集保护、自锁、权限基线冲突回滚、planned/未知代码拒绝。

组件验证分组、筛选、受限选择、局部操作、草稿切换、按键重试与只读。真实浏览器验证管理员按模块保存角色后，受限账号重新请求会话/页面只能执行获授操作，直接 API 越权 403；planned 模块不可授予。旧 ABC 浏览器主链继续通过。

最终在一次性 PostgreSQL 和网关运行冻结安装、API/Web/真实 PG、contracts:check、归档隔离、production build、Compose 配置/运行、Playwright 和现有 acceptance:phase-1/phase-2。phase-2 脚本仅四项回归，不宣称补齐原平台深度业务验收。依赖复用 NTFS；测试秘密不入 Git，销毁一次性资源，任何受阻清理如实记录。验收后更新 README、OPENAPI、ACCOUNT-ADMINISTRATION、FOUNDATION 和 PHASE-2，沿既有授权本地合并并更新预览，不推送。
