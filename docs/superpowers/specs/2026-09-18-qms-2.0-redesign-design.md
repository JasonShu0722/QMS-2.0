# QMS 2.0 重构设计规格

- 日期：2026-09-18
- 状态：已确认，待新对话编制实施计划
- 适用范围：QMS 2.0 产品、架构、交互、数据、部署与实施边界
- 决策方式：基于 2026-09-18 的逐节设计沟通确认

## 1. 背景

当前 QMS 1.0 已形成前后端与部署骨架，但产品效果未达到继续迭代的要求。主要问题不是单个页面缺陷，而是产品边界、领域模型和交互架构发生了系统性偏差：

1. 预览环境与双轨逻辑增加了代码、数据和运维成本，但没有产生足够业务价值。
2. 面向页面和模块建设了过重的功能开关体系，且与权限、发布控制边界混淆。
3. 问题中心把“统一管理”错误实现为“统一表单和统一流程”，既损失业务差异，也没有形成可靠的统一状态与协作链路。
4. 问题事项存在来源编号、统一问题编号和 8D 编号并存，编号嵌入了易变的分类与处理方式语义。
5. 问题跟进与审批缺乏可视化配置能力，不同业务类型难以维护自己的流程。
6. 登录后的菜单、工作台和页面布局没有围绕用户任务组织，列表与处理页面之间缺乏连续工作上下文。

QMS 2.0 采用并行重建策略，不在 1.0 代码上进行原地修补。

## 2. 目标

QMS 2.0 必须实现以下目标：

- 形成面向内部员工和供应商的统一入口与身份分流。
- 以业务领域组织内部 QMS，以供应商任务语言组织供应商门户。
- 建立“业务域专属模型 + 薄公共问题索引”的问题管理架构。
- 实现一事一号，简报与 8D 切换不更换编号。
- 建立受控、可视化、可版本化的流程设计与运行能力。
- 提供高质量企业界面、复杂表单、业务台账和问题处理工作空间。
- 采用单人可维护、未来可扩展的模块化单体架构。
- 面向公网云部署，从首版具备账号安全、供应商隔离、审计、备份和恢复能力。
- 以可操作、可联调、可闭环、可授权、可验证为完成标准。

## 3. 非目标

首期明确不建设：

- 预览环境或双轨发布体系。
- 微服务和 Kubernetes。
- 通用 BPMN 平台。
- 旧调试数据迁移。
- 面向普通业务功能的大规模功能开关。
- AI 自动决策。
- 外部身份平台集成。
- 为尚未出现的并发规模预建复杂缓存和消息基础设施。

## 4. 重启与归档策略

### 4.1 采用同仓库并行重建

QMS 1.0 保留为只读参考资产，QMS 2.0 在同一仓库的独立目录中建设。不得在 1.0 目录中继续开发 2.0 功能，也不得通过长期兼容层维持两套模型。

```text
QMS/
├─ archive/
│  └─ qms-1.0/
│     ├─ backend/
│     ├─ frontend/
│     ├─ deployment/
│     ├─ docs/
│     └─ ARCHIVE_MANIFEST.md
├─ qms-2.0/
│  ├─ apps/
│  ├─ deployment/
│  ├─ docs/
│  └─ README.md
├─ AGENTS.md
└─ README.md
```

### 4.2 归档规则

- 归档以执行归档时的实际工作区为准，包含当前未提交修改。
- 归档被定义为开发快照，不宣称为可交付版本。
- `ARCHIVE_MANIFEST.md` 必须记录来源提交、未提交文件清单、归档日期、已知缺陷、验证状态和禁止继续开发声明。
- 归档目录不得参与构建、测试、依赖安装、容器启动或生产部署。
- 归档完成后建立独立基线提交和快照标签。
- 2.0 使用独立依赖、数据库迁移链、容器入口和文档体系。
- 根目录只保留跨版本治理文件。

## 5. 产品与应用边界

### 5.1 登录与身份分流

内部员工与供应商共用同一个登录入口。登录成功后由服务端根据账号身份分流：

- 内部账号进入内部 QMS。
- 供应商账号进入供应商门户。
- 界面不提供内部 QMS 与供应商门户的人工切换按钮。
- 首期使用 QMS 独立账号；外部身份平台绑定作为未来独立能力。

### 5.2 内部 QMS

内部菜单按业务领域组织：

- 综合工作台
- 供应商质量
- 制程质量
- 客户质量
- 新品质量
- 审核管理
- 问题中心
- 数据分析
- 系统管理

问题中心只承担跨业务域聚合、检索、跟踪、升级预警和统计，不提供通用问题创建入口。

### 5.3 供应商门户

供应商门户拥有独立的信息架构，不是内部页面的权限裁剪版本。首期包含：

- 综合待办
- 问题回复与整改
- 简报与 8D 处理
- 资料和附件提交
- 绩效与评价结果
- 账号和企业资料

### 5.4 共享底座

两个应用界面共享：

- 账号认证和身份分流
- 角色、功能权限和数据范围
- 受控流程定义与运行
- 问题编号、待办、通知、审计和附件
- 问题聚合、报告预览和追溯

## 6. 界面与交互架构

### 6.1 综合工作台

登录后的第一屏为综合工作台，同时呈现：

- 个人待办和待审批
- 即将逾期事项
- 高风险问题
- 关键质量指标与趋势
- 常用业务入口

工作台不是模块入口集合页，必须帮助用户判断“当前最需要关注和处理什么”。

### 6.2 导航

- 在综合工作台状态下完整展示业务领域导航，保证功能可发现。
- 进入具体业务域后，主导航自动收缩为图标轨。
- 图标轨旁展开当前业务域的上下文菜单。
- 返回综合工作台时恢复完整业务导航。
- 图标体系、颜色和品牌视觉在后续专项设计中定义，不影响本规格中的信息架构。

### 6.3 内部工作标签

- 点击业务台账记录直接打开完整处理页。
- 默认在系统内部创建工作标签，并提供快捷操作另开浏览器页签。
- 只有一个工作页时不显示额外标签栏。
- 多个工作页时显示 32 至 36 像素高的单行标签栏。
- 标签永不换行；超出数量后，保留当前和最近标签，其余进入“全部已打开”面板。
- 同一业务记录重复点击只激活已有标签。
- 处理页支持专注模式，允许临时收起业务导航与上下文侧栏。
- 标签状态可以恢复，但非活动页面不得长期保留完整 DOM 和大体积数据状态。

### 6.4 业务台账

- 默认显示业务域内当前用户有权访问的全部问题。
- 默认视图为精简表格；状态看板按业务需要开放切换。
- 默认字段包括编号、标题、来源、严重度、状态、责任方、负责人、截止时间和更新时间。
- 行内不堆叠大量操作按钮，点击记录进入完整处理页。
- 用户可按业务台账保存字段显隐、顺序、宽度、固定列、筛选、排序和视图类型。
- “我的待办”“我发起的”“我关注的”等作为快捷个人视图，不替代业务总台账。

### 6.5 问题处理工作空间

处理页采用 Blendex 8D Workspace 所体现的空间模型，但不复制其固定 D0 至 D8 业务规则：

- 默认进入“问题概览”，首先展示完整问题档案。
- 左侧显示流程完成度和处理节点。
- 流程节点由受控流程定义动态生成。
- 中间为当前节点或问题概览的宽幅工作区。
- 顶部提供工作区、报告预览和追溯记录视图。
- 简报使用精简流程，8D 使用完整流程。
- 流程动作、审批意见和沟通轨迹必须留在同一业务上下文中。
- 页面避免多层嵌套标签；完整问题信息使用结构分区和锚点导航。

## 7. 领域模型

### 7.1 薄公共问题索引

公共问题索引只保存跨模块管理所需字段：

- 内部 UUID
- 对外问题报告编号
- 业务域和问题类型
- 来源单据引用
- 严重度和当前状态
- 责任方和负责人
- 截止时间
- 流程实例引用
- 升级、关闭和归档信息
- 创建与更新时间

公共索引不是通用业务表单，不保存各业务域的全部专业字段。

### 7.2 业务域专属模型

供应商、制程、客户、新品和审核模块分别保存自己的专业字段、附件、验证规则和业务关系。公共问题索引通过稳定引用与业务记录关联。

问题中心读取公共索引，并按需加载业务详情。业务域负责创建和维护问题事实，问题中心不反向拥有业务记录。

### 7.3 编号

- 一个业务问题从创建到关闭只有一个对外问题报告编号。
- 简报和 8D 使用同一编号。
- 从简报升级为 8D 时编号保持不变。
- 默认格式为 `ZXPR-<稳定分类码>-<YYMM>-<三位流水号>`。
- 分类码来自创建时的业务来源分类，不使用严重度、处理形式或当前阶段等可变字段。
- 编号创建后永久不可变。
- 编号规则按版本保存，规则变更不影响历史编号。
- 内部关联使用 UUID，业务代码不得解析编号字符串推断权限或状态。

## 8. 受控流程平台

### 8.1 流程设计器

流程设计器支持以下受控节点：

- 处理
- 审批
- 验证
- 抄送
- 驳回
- 退回
- 重开
- 关闭

节点可配置角色、处理人规则、时限、提醒、升级和有限条件分支。设计器不允许执行任意脚本，不提供完整 BPMN 语义。

### 8.2 流程版本

- 流程按业务域、问题类型和回复形式绑定。
- 流程发布后生成不可变版本。
- 已运行实例固定使用创建时的流程版本。
- 新版本只影响新建问题。
- 版本必须保存发布人、发布时间、变更说明和结构快照。

### 8.3 简报升级为 8D

- 保留问题编号、来源记录、现有附件和审计轨迹。
- 记录升级人、升级时间和原因。
- 创建对应的 8D 流程实例版本。
- 共通字段可以显式映射，但不得静默覆盖人工内容。
- 升级过程在单个事务中完成；失败时整体回滚。

## 9. 权限模型

权限由三个独立维度共同决定：

1. 功能权限：用户是否可以执行某类操作。
2. 数据范围：用户可以访问哪些业务记录。
3. 流程权限：当前节点由谁处理、审批或验证。

供应商账号只能访问本企业相关数据。供应商企业范围必须由服务端会话解析，不能信任客户端提交的企业 ID。

权限与运行控制完全分离。功能开关只保留外部接口、试验功能和紧急熔断用途，不参与日常权限治理。

## 10. 技术架构

### 10.1 技术栈

- 前端：React 19、TypeScript、Vite、Ant Design 6。
- 服务端状态：TanStack Query。
- 工作标签等界面状态：轻量本地状态库。
- 流程设计器：React Flow。
- 后端：NestJS 11 模块化单体。
- 数据库：PostgreSQL 18。
- ORM：稳定版 Prisma 7；首期不采用候选阶段的 Prisma 8。
- API：REST + OpenAPI，并自动生成前端请求类型。
- 文件：S3 兼容对象存储。
- 包管理与 Monorepo：pnpm workspace；首期不引入 Nx 或 Turborepo。

### 10.2 模块化单体

后端按领域模块组织，模块通过显式服务接口和领域事件协作。建议首期模块：

- identity
- authorization
- organization
- supplier-quality
- process-quality
- customer-quality
- new-product-quality
- audit-management
- problem-index
- workflow
- task-notification
- file-management
- audit-log
- system-configuration

禁止业务模块直接读取其他模块的内部表。跨模块查询通过公开服务或专门读取模型完成。

### 10.3 后台任务

- API 与 Worker 使用同一代码仓库和应用镜像，通过不同启动入口运行。
- 首期使用 PostgreSQL 任务表和事务性 Outbox。
- 通知、催办、超时、升级和报告生成由 Worker 异步处理。
- 任务采用有限重试和失败队列。
- 只有在可证明的吞吐或延迟问题出现后，才评估 Redis 或专用消息队列。

## 11. 部署架构

生产环境使用“应用服务器 + 托管 PostgreSQL + 对象存储”：

```text
公网 HTTPS
   ↓
反向代理 / TLS
   ├─ React 静态应用
   └─ NestJS API
        ├─ Worker
        ├─ 云 PostgreSQL
        └─ 云对象存储
```

- 单台应用云服务器通过 Docker Compose 运行反向代理、Web、API 和 Worker。
- 数据库和附件使用云厂商托管服务。
- 应用容器无状态，可以从镜像和配置重建。
- 只存在本地开发、CI 临时验证和正式生产三种运行场景。
- CI 验证资源执行完成后立即销毁，不提供长期可登录的预览环境，也不连接生产数据库。

## 12. 安全基线

- 密码使用 Argon2id 加盐哈希。
- 使用服务端会话和不可预测的随机 Session ID。
- Session 仅通过 `Secure`、`HttpOnly`、`SameSite` Cookie 传递。
- 浏览器本地存储不得保存 Session ID、JWT 或刷新令牌。
- 写操作使用 CSRF 防护。
- 登录、密码重置和敏感操作执行账号与 IP 组合限流。
- 连续失败后采用递增等待和验证码，不使用永久锁定作为默认策略。
- 系统管理员强制 MFA；普通内部账号和供应商账号首期可选，并支持按角色强制。
- 密码重置、MFA 变更、权限变更和会话撤销必须记录安全审计。
- API 对外使用统一安全错误，不返回堆栈、SQL 或内部路径。
- 数据导出、流程变更、审批、驳回和附件操作必须记录业务审计。
- 密钥和数据库口令只进入云端密钥管理或部署环境，不进入仓库。

## 13. 核心数据流

### 13.1 创建问题

1. 用户从业务域创建问题。
2. API 校验功能权限、数据范围和业务字段。
3. 编号服务生成唯一问题报告编号。
4. 在一个数据库事务中创建业务记录、公共问题索引、流程实例、审计事件和 Outbox 事件。
5. 事务提交后由 Worker 生成待办并发送通知。
6. 问题中心通过公共索引展示新问题。

### 13.2 处理问题

1. 用户从业务台账进入问题概览。
2. 用户进入当前节点并提交处理内容。
3. API 校验流程版本、当前节点、处理权限和数据版本。
4. 在一个事务中更新业务数据、流程状态、审计记录和 Outbox 事件。
5. Worker 异步完成通知、催办、超时和升级。

### 13.3 并发与幂等

- 创建、审批、节点提交和升级支持幂等键。
- 可变业务记录使用乐观锁版本号。
- 数据版本冲突返回 HTTP 409 和用户可理解的刷新提示。
- 后提交者不得静默覆盖先提交者的数据。

## 14. 附件与证据

- 限制文件类型、大小和数量。
- 文件名不作为对象存储键。
- 数据库记录文件哈希、业务归属、上传人、版本和审计信息。
- 供应商文件上传后进入隔离状态，完成安全扫描后才能下载或进入报告。
- 删除默认采用逻辑删除和保留期。
- 对象存储启用版本控制或回收保护。

## 15. 错误处理与恢复

- API 错误响应包含稳定业务错误码、用户信息、字段错误和追踪 ID。
- 前端根据错误类型展示字段反馈、冲突提示或可重试状态。
- 异步任务采用有限重试；失败任务进入可查询、可人工重试的失败队列。
- 云数据库启用自动备份和时间点恢复。
- 对象存储启用版本保护。
- 定期执行恢复演练，验证数据库、附件和应用配置能够联合恢复。

## 16. 测试与完成标准

### 16.1 自动化验证

- 前端组件与状态逻辑：Vitest + Testing Library。
- 后端领域逻辑、权限、流程和编号：NestJS 单元测试。
- 数据库行为：临时真实 PostgreSQL 集成测试，不用 SQLite 替代关键验证。
- API 契约：OpenAPI 生成类型，并在 CI 检查未同步变更。
- 主链路：Playwright 端到端测试。
- 供应商隔离：每个场景同时验证允许访问和拒绝访问。
- 关键写操作：重复请求、并发冲突和事务回滚测试。

### 16.2 完成标准

一个功能只有同时满足以下条件才可标记完成：

- 页面可以完成真实操作。
- API 与前端契约一致。
- 数据能够完成业务闭环。
- 功能权限、数据范围和流程权限均有验证证据。
- 通知、审计、附件和失败恢复符合该功能要求。
- 相关测试、构建和迁移通过。
- 产品规格、接口说明和验证口径同步更新。

页面、接口、模型或路由存在，不等于功能完成。

## 17. 实施批次

### 批次 0：冻结与归档 1.0

- 保存当前未提交修改。
- 建立归档目录与归档清单。
- 创建归档基线提交和快照标签。

## 18. 风险与回退

### 18.1 主要风险

- 受控流程设计器范围膨胀为通用 BPMN 平台。
- 为追求视觉效果而牺牲复杂表单的可用性。
- 公共问题索引重新演变为统一大表单。
- 供应商数据范围在新接口中遗漏。
- 单人开发同时铺开多个业务域，导致底座未稳定即扩张。
- 归档目录意外进入构建、扫描或部署流程。

### 18.2 控制措施

- 流程节点类型和条件表达式使用白名单。
- 首个业务域只选择供应商质量，其他模块等待主链路验证。
- 公共问题索引字段变更需要领域边界评审。
- 供应商隔离测试列为每个接口的强制验收项。
- 归档目录在包管理、CI、容器构建和代码扫描中显式排除。

### 18.3 回退思路

- 1.0 归档和快照标签提供代码恢复能力。
- 2.0 在独立目录、数据库和部署入口中建设，不修改 1.0 运行数据。
- 2.0 正式切换前不替换现有入口。
- 每个 2.0 里程碑使用可回滚容器镜像和向前数据库迁移。
- 生产变更失败时回退应用镜像；涉及不可逆数据变化时使用备份和恢复演练方案处理。

## 19. 已确认决策

- 同仓库并行重建，先归档 1.0。
- 1.0 归档包含当前未提交修改。
- 2.0 不迁移现有调试数据。
- 内部账号和供应商账号共用登录入口并自动分流。
- 内部菜单按业务领域组织。
- 供应商门户使用独立信息架构。
- 综合工作台同时呈现任务与质量态势。
- 问题中心只聚合，不创建通用问题。
- 简报和 8D 一事一号，升级不换号。
- 使用中性编号前缀和稳定分类码。
- 使用受控流程设计器，不建设完整 BPMN。
- 列表采用可配置台账和按需看板。
- 处理页默认进入问题概览。
- 使用智能单行内部工作标签。
- 技术栈为 React + NestJS + PostgreSQL。
- 架构为模块化单体。
- 生产部署为应用云服务器 + 托管 PostgreSQL + 对象存储。
- 系统管理员强制 MFA，其他账号首期可选。
- 供应商质量是首个业务试点。
