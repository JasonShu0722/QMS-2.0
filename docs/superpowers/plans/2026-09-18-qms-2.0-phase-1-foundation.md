# QMS 2.0 批次 1：工程与底座实现计划

> **面向 AI 代理的工作者：** 必需子技能：使用 `superpowers:subagent-driven-development`（推荐）或 `superpowers:executing-plans` 逐任务实现此计划。步骤使用复选框（`- [ ]`）语法来跟踪进度。

**目标：** 在已经冻结的 QMS 1.0 归档之外，建立可独立启动、可测试、可部署的 QMS 2.0 工程与安全底座，完成统一登录、身份分流、权限与供应商数据范围、审计、附件能力和应用外壳；本计划不实现任何业务域闭环。

**架构：** `qms-2.0/` 是独立的 pnpm workspace，包含 React Web、NestJS 模块化单体 API、共享 OpenAPI 类型和本地开发依赖。API 使用 PostgreSQL + Prisma，服务端会话通过安全 Cookie 传递，Web 只保存查询缓存和工作标签 UI 状态；Worker 与 API 共用后端代码但使用独立启动入口。归档目录不进入 workspace、依赖安装、测试、容器构建或 CI。

**技术栈：** React 19、TypeScript、Vite、Ant Design 6、TanStack Query、Zustand、NestJS 11、REST/OpenAPI、PostgreSQL 18、Prisma 7、Argon2id、S3 兼容对象存储、Vitest/Testing Library、Jest、真实 PostgreSQL 集成测试、Playwright、pnpm workspace、Docker Compose。

---

## 范围与完成门槛

本批次包括：工程骨架、数据库迁移链、独立账号登录、内部/供应商服务端分流、功能权限、组织数据范围、会话与 CSRF、审计事件、附件元数据和对象存储适配、Outbox/Worker 基础、综合工作台骨架、业务导航、上下文菜单和内部工作标签。

本批次明确不包括：供应商质量或其他业务域字段与闭环、公共问题索引、问题编号服务、流程设计器与流程运行时、待办通知业务规则、看板指标、简报/8D、报告预览、旧数据迁移、QMS 1.0 兼容层、外部身份平台、Redis/Kafka、预览环境和 Kubernetes。它们属于批次 2 及以后，不能通过“先放一个临时实现”进入本批次。

离开本批次前必须同时满足：

- `pnpm --dir qms-2.0 install --frozen-lockfile` 可重复完成，workspace 不解析 `archive/qms-1.0`。
- PostgreSQL 迁移、种子账号、API、Worker、Web 和 MinIO 本地 Compose 可启动。
- 内部账号只能进入内部壳，供应商账号只能进入供应商壳；不存在手工切换入口。
- 会话、CSRF、限流、Argon2id、统一安全错误、权限和供应商组织隔离均有自动化验证。
- OpenAPI 文档与生成的前端请求类型在 CI 中保持同步。
- 归档隔离检查、Web/API/集成/E2E 测试、生产构建和 Compose 配置校验均通过。

- [ ] **步骤 3：实现密码和会话最小闭环。** `PasswordService` 使用 Argon2id；成功登录生成 32 字节随机 Session ID，仅将 SHA-256 哈希写入 `Session`，原始值只写入 `Secure`、`HttpOnly`、`SameSite=Lax` 的 `qms_session` Cookie。生产环境强制 `Secure=true`，开发环境也保留 `HttpOnly`/`SameSite`。

```ts
const rawSessionId = randomBytes(32).toString('base64url')
await prisma.session.create({ data: { tokenHash: sha256(rawSessionId), userId, expiresAt } })
res.cookie('qms_session', rawSessionId, {
  httpOnly: true,
  secure: config.isProduction,
  sameSite: 'lax',
  path: '/',
  maxAge: SESSION_MAX_AGE_MS,
})
```

- [ ] **步骤 4：实现 CSRF、限流和服务端身份分流。** `GET /api/v1/auth/csrf` 发放非 HttpOnly 的随机 `qms_csrf` Cookie；所有写请求要求 `x-csrf-token` 与 Cookie 值相等。限流 key 使用规范化账号标识与客户端 IP 的 HMAC，不把原始账号写入日志。成功响应只返回 `{ accountType, landingPath }`，`INTERNAL` 固定为 `/app/workbench`，`SUPPLIER` 固定为 `/supplier/inbox`；前端不能提交企业 ID 来改变分流。
