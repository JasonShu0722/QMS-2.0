## 1. 前置交付的结果

1. 将原组织结构与部门岗位合为“组织与岗位”入口，左侧架构树下穿部门 / 科室，右侧管理所选节点的基本信息、岗位和人员任职，保留同一份底层数据。
2. 组织、部门代码可在原对象上编辑，内部 ID、权限来源及历史引用保持可追溯。
3. 已确认误建且未使用对象有真实受控删除入口；有下级 / 岗位 / 有效或历史任职 / 业务引用时阻止直接删除并明确依赖，不级联删除业务数据。停用须先处理有效任职、管理职责、启用下级、在途责任及生效配置依赖，不自动批量迁移；只有历史引用时可保留并停用，新业务不再选择，保护必要管理入口。
4. 获准上线并验收后，管理员可以在正确入口维护真实公司结构，不再被迫用新增子组织代替新增部门。
5. 管理员作为组织岗位，通过岗位权限及人员任职取得本组织内全部适用功能权限，不新增另一套独立管理员业务角色或仅按账号名称放行。

本次基础管理不以提前实现动态审批为前置；经理 / 部长职责岗位关联、动态人员解析、并行及轮次在下一流程基础交付中补齐。其所需的部门 / 科室 / 岗位身份必须复用本单元成果，不能另建影子架构。

已确认同部门可有两名部长，部长需要关联分管科室，同一科室不会同时由两名部长分管；后续管理职责配置必须支持该关系，不将部长限制为每部门一人。动态审批按本单责任科室匹配分管部长及有效任职；建议分管范围可在具体部长任职上维护，以支持同岗位多人，不另建影子角色或重复账号。同科室同期重叠配置受控拒绝并保留输入 / 既有配置，任职及分管历史保留；不建设多部长会签或任意代批机制。

### 1.1 已确认的统一管理工作区

平台管理保留一个“组织与岗位”页签，原两个管理入口收敛为同一工作区，不长期保留可各自编辑的平行界面。顶部管理组织和左侧树共享同一授权上下文，不能显示不同组织的数据。左树默认组织 / 部门 / 科室，岗位及任职以右侧列表呈现，不将所有人员塞入架构树。

| 选择对象 | 右侧内容及动作 |
| --- | --- |
| 组织 | 基本信息、直属部门、明确区分的新增部门 / 新增子组织、代码修改、启停及受控删除 |
| 部门 / 科室 | 基本信息、下级结构、所属岗位、人员任职；新增岗位带入当前部门，后续管理职责岗位关联复用此位置 |
| 岗位列表记录 | 编辑岗位、岗位权限、有效任职人员及历史；复用已有岗位权限抽屉及任职预览，不新增独立角色配置 |

人员任职仍允许兼岗，按已有多任职关系判断，不为当前树选中节点另存一份用户部门或主岗。用户账号创建 / 编辑继续留在用户管理，岗位任职数据共用，不在组织工作区重建账号系统。旧账号定位链接及已保存工作标签按当前路由能力受控衔接，不将无效目标静默跳到首条记录。

统一入口的可见性按实际可用组织 / 结构权限组合开放，各区域独立校验；只有结构读取权限的人不应被强制要求组织管理权限才能查看岗位，未授权组织不为补全树而泄露名称 / 人数。代码和 API 仍区分授权组织、Department、Position，不为视觉整合合表或迁移真实数据。

### 1.2 管理员全量权限岗位

将管理员纳入已有“组织 → 部门 / 岗位 → 权限 → 用户任职”的业务链，归属既有部门及组织范围，具体挂在哪个部门随真实架构维护，不强制虚构信息管理部门。岗位权限以统一有效权限目录配置本组织全部适用功能，普通员工岗位按业务分工配置；岗位名称或用户名包含 admin 不构成授权依据。

全量指本授权组织的适用功能权限，不自动获取所有其他授权组织 / 供应商边界，也不以管理员身份跳过数据范围、单据职责、版本锁定、删除引用检查或审批有效性条件。已有已确认的业务限制继续生效，例如管理员可按专门授权修订风险，但不能伪造经理 / 部长签批或仅凭管理员身份调整已限制给对应工程师的来源范围。

新增权限随版本目录核查及明确配置补齐，不能通过未经审阅的通配符、隐藏超管判断或临时扩权解决未配置项；初次配置复验实际操作者授予上限、自锁保护及授权预览。旧管理账号、直接角色及兼容岗位来源先只读核对，不自动删除 / 合并 / 清空，也不因创建管理员岗位就给全体管理员账号重复任职。初始化 / 任职转换的具体对象与授权在实施设计中按实际证据落实。
