**目标：** 将包含当前未提交修改的 QMS 1.0 工作区冻结为受版本控制、只读的归档基线，并切断其与活跃构建、CI 和部署入口的连接；本阶段不编写任何 QMS 2.0 业务代码。

**架构：** 将 1.0 的应用、部署、历史规格、CI 和运行说明移动至 `archive/qms-1.0/`，保留 Git 历史可追溯性并在归档目录内生成不可含密钥的清单。仓库根目录只保留跨版本治理、2.0 设计与实施计划；`qms-2.0/README.md` 仅作为空的版本边界声明，不创建包清单、应用、数据库迁移或容器入口。归档基线提交完成后以注解标签固定快照。

## 风险与回退

| 风险 | 控制措施 | 回退方式 |
| --- | --- | --- |
| 移动时遗漏未提交或未跟踪文件 | 先保存三份状态证据，使用 `git mv`，并对当前 16 项执行存在性断言 | 在基线提交和标签完成前，使用 `git status` 与 `git diff --cached` 找回；提交后从标签以新分支恢复，不修改归档本身。 |
| 归档意外触发旧 CI 或部署 | 移走根 `.github/workflows`、根 Compose 与根应用目录，并断言它们不存在 | 从快照标签创建临时恢复分支，只在明确授权的隔离环境中恢复；不把旧目录重新放回 `main`。 |
| 本机服务仍占用移动中的目录 | 归档前仅执行本机 `docker compose down`，不删卷 | 服务停止后仍可用现有 Docker 卷恢复；本计划不接触远程部署或托管数据库。 |
| 密钥或运行数据被纳入归档 | 只用路径和 Git 元数据生成清单，保持忽略规则，绝不读取 `.env` 正文 | 若意外暂存疑似机密，在提交前从索引移除该具体路径并轮换受影响凭据；不要在 Git 历史中保留。 |
| 误把阶段 0 扩展为 2.0 开发 | `qms-2.0/` 仅允许 README，验证命令强制检查 | 任何新增 2.0 工程文件均从本阶段变更集中撤出，另立后续批次计划。 |
