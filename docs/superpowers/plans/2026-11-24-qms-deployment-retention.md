# QMS 部署存储维护与失败处理

## 当前摘要

- 目标是限制生产部署产生的历史镜像、迁移快照和构建缓存，并按迁移阶段区分恢复与告警。
- 2026-11-24 负责人批准实施、与流程管理一同合并部署。[Issue #171](https://github.com/JasonShu0722/QMS-2.0/issues/171) 跟踪部署维护，[PR #170](https://github.com/JasonShu0722/QMS-2.0/pull/170) 承载联合发布，流程管理继续关联 #169 和 REQ-0044。
- 部署和保留脚本已经实现。构建缓存按 builder 范围回收，直接执行和首次生产发布均默认预览。首次删除等待实际生产候选清单审阅。
- 本地治理检查、Bash 语法和部署／CI 定向回归 42 项通过。在一次性 Docker 29.10.0 验证了预览、实际清理、部署锁和两档缓存清理。迁移前恢复、迁移报错和探活故障以隔离的脚本控制流验证。

## 实施顺序

1. 复核三份 Compose 配置和 CI 的 SSH 交付方式。复用生产锁、SHA 校验、加密备份、迁移和探活命令。
2. 实现独立清理入口，保护实际容器引用及最近 3 套完整历史镜像，按快照保留 14 天，同步清理配对密钥。用 `DRY_RUN=1` 在锁内输出清单，记录镜像与备份所在文件系统的实际变化。普通删除失败保留告警。
3. 在构建前检查 Docker 与快照文件系统余量。迁移前的失败核实或恢复上一成功 SHA 的应用，迁移开始后将未知结果持久记录，直至新的部署通过全部健康检查，失败留证并返回非零。成功标记后执行清理，清理异常时保留健康发布结果。
4. 先写回归并记录红灯，再实现和复测。运行 `bash -n`、部署脚本定向回归、`corepack pnpm check:governance`、`git diff --check`，用一次性 Linux Docker 和临时备份目录验证真实保留、释放和失败分界。先规格审查，再质量审查。
5. 将 #171 实现以独立提交纳入 #170，核对最终提交范围和 CI，推进联合合并和首次自动部署。首次发布记录生产 `DRY_RUN=1` 清单和部署 SHA。负责人审阅后开启实际清理，复查服务健康、存储前后差异和 builder 使用范围。完成后回填实际证据，原 REQ 继续按业务验收约定处理。
